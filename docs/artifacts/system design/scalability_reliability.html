Scalability & Reliability

How to grow without rewriting everything — and how to fail without taking the whole system down. Plain-language CAP, the reliability toolbox, and where DashNote already sits on each pattern.

Full curriculum Architect + backend FastAPI · NestJS

00 Overview

Scale is about capacity under load. Reliability is about correct behavior under failure. You need both: a fast system that lies, or a correct system that melts at 2× traffic, both fail users.

What this book covers
  1. Vertical vs horizontal scale; why stateless wins
  2. Load balancers, read replicas, sharding intuition
  3. CAP / PACELC — pick consistency where it matters
  4. Timeouts, retries+jitter, breakers, bulkheads
  5. Degradation, health probes, idempotent handlers
Client→ LB→ Stateless API × N→ Primary DB+ Replicas / cache / queue
DashNote today
FastAPI + Uvicorn, single API container behind Nginx, Postgres primary, Redis, ARQ workers (scalable with --scale worker=N). JWT is mostly stateless; refresh/blacklist need Redis for multi-instance. Strong degradation story; weak on breakers, probe split, API replicas.

Part 7 · Scalability foundations

01 Vertical vs horizontal

Two ways to handle more work. Most systems do both — but in a deliberate order.

Vertical (scale up)

Bigger machine: more CPU, RAM, disk IOPS. Simple — same code, same topology.

  • Pros: no distributed pain
  • Cons: hard ceiling, single blast radius, expensive

Horizontal (scale out)

More identical instances behind a load balancer. Requires shared-nothing app design.

  • Pros: linear-ish capacity, rolling deploys
  • Cons: state, consistency, coordination
Rule of thumb
Vertical-first for the DB until you understand the bottleneck; horizontal-first for stateless compute (API, workers). Don’t shard Postgres on day one.
LayerUsual first moveLater
API / workers Horizontal replicas Autoscale (HPA / ASG)
Postgres Vertical + indexes + pool Read replicas → then shard
Redis / Qdrant Vertical or managed tier Cluster / partitioning
DashNote · Partial
Workers: docker compose up --scale worker=3 + WORKER_MAX_JOBS. API: one container (container_name pins a single instance). Prod leans on managed data plane (fat Postgres/Redis/Qdrant), thin compute — see docs/documentation/qs.md.

02 Stateless services

A service is stateless if any replica can handle any request — no local memory required between calls. Session data lives in the client (JWT) or a shared store (Redis).

Stateless

JWT access token validated locally. Scale by adding pods. No sticky sessions.

Shared state

Refresh tokens, blacklist, rate limits, cache — in Redis. All replicas agree.

Sticky (avoid)

In-memory sessions + ip_hash. Breaks deploys and uneven load. Rarely worth it.

Gotcha
“Stateless JWT” + “logout must revoke immediately” ⇒ you still need a shared blacklist or short TTL. Pick one: short-lived access tokens, or Redis revocation.
DashNote · Covered
Access JWT validated in-process (src/auth/security.py). Refresh tracking + access blacklist in Redis (src/core/redis/redis.py). Falls back to pure JWT when Redis is off — fine for single instance; require Redis for multi-replica auth.

03 Load balancing

An LB distributes requests across healthy instances. Algorithms matter less than health awareness and connection draining.

AlgorithmWhenWatch for
Round-robin / least-conn Default for HTTP APIs Slow instances still get traffic without good health checks
Weighted Canary / mixed sizes Weights drift from reality
IP hash / sticky Legacy in-memory session Uneven shards; prefer shared state instead
Client→ Nginx / ALB→ api-1 api-2 api-N
  • LB should use readiness (not liveness) to decide who gets traffic.
  • On deploy: stop new traffic → drain in-flight → shut down (graceful).
  • Edge rate limits (limit_req) protect the fleet, not just one process.
DashNote · Partial
Nginx upstream api_upstream { server api:8000; } — single member + keepalive. Edge limit_req at 10r/s. No multi-replica upstream or Docker DNS round-robin yet. Should be: remove fixed container_name for API; upstream to api:8000 with N replicas (or managed LB).

04 Read replicas

One primary accepts writes. Replicas copy changes asynchronously and serve reads. You buy read capacity — and accept replication lag.

Route to primary

  • All writes
  • Read-your-writes (just created note)
  • Auth / billing / money

Route to replica

  • List / search / analytics
  • Reports that tolerate seconds of lag
  • Heavy read fan-out
Intuition
After POST /notes, the next GET should hit the primary (or wait for lag). DashNote’s note create is already sync to Postgres; search indexing is async via ARQ — same mental model as “replica lag,” just for vectors.
DashNote · Gap
Single DATABASE_URL, one Postgres service. Engine uses pool_pre_ping=True only — no read/write split. Should be: DATABASE_READ_URL + lag-aware routing for list/search when reads dominate.

05 Sharding intuition

Sharding splits data across many databases by a key (e.g. workspace_id). It’s a last resort — operationally expensive.

When you need it

Single primary can’t hold the working set or write QPS even after replicas + vertical scale.

Shard key

Pick a key that keeps related rows together (workspace). Cross-shard joins become application joins.

Before sharding

Indexes, caching, CQRS/async, read replicas, archive cold data, partition tables in one DB.

DashNote · Covered (logical only)
Tenancy is workspace_id filters — logical isolation, not physical shards. That’s the right shard key if you ever need one. Don’t invent physical shards yet.

06 CAP / PACELC in plain language

During a network partition you cannot have perfect Consistency and Availability together. PACELC adds: even when the network is fine, you still trade Latency vs Consistency.

TermPlain English
Consistency Every read sees the latest successful write (or an error).
Availability Every non-failing node still answers (maybe with stale data).
Partition The network splits; nodes can’t talk. You must choose C or A.
PACELC If Partition → A/C; Else → Latency vs Consistency. Most “AP” systems also choose L over C in the happy path.

Pick consistency where it matters

Strong (CP-ish)

  • Register user + workspace + membership (one DB txn)
  • Payments, permissions, “delete forever”
  • Idempotency-key claim

Eventual (AP / low latency)

  • Search index / embeddings
  • Caches, analytics counters
  • Notifications, “recently viewed”
Design habit
Don’t ask “are we CP or AP?” Ask per operation: “If this is wrong for 5 seconds, is that a bug or a feature?”
DashNote · Covered
Auth register + CRUD commits: strong (Postgres txn). Note → embed → Qdrant: eventual via ARQ; event bus never blocks HTTP (src/shared/events/bus.py). Classic CQRS-lite — write path sync, search path async.

Part 8 · Reliability patterns

07 Timeouts

A timeout is a budget. Without one, a slow dependency holds your threads/connections forever and cascading failure begins.

  • Connect timeout — fail fast if you can’t open a socket.
  • Read / request timeout — max wait for a response.
  • Deadline propagation — remaining budget passed downstream (harder, best).
Layering
Client (browser) > edge proxy > API handler > outbound HTTP/DB. Inner timeouts should be shorter than outer ones so the outer layer doesn’t give up first while the inner still works.
DashNote · Partial
Present: QDRANT_TIMEOUT, AGENT_TOOL_TIMEOUT, ARQ job_timeout=300, Docker healthcheck timeouts. Missing: DB statement_timeout, global request timeout middleware, explicit LiteLLM/httpx timeouts everywhere, Nginx proxy_read_timeout tuned.

08 Retries with jitter

Retry only transient failures (timeouts, 503, connection blips). Never blindly retry non-idempotent POSTs. Always add jitter so thundering herds don’t sync up.

Do retry

  • Network blips, 429/503
  • Idempotent GETs / upserts
  • With exponential backoff + jitter

Don’t retry

  • 400 / 401 / 403 / 404
  • Non-idempotent create without a key
  • Business logic errors
# wait = min(cap, base * 2^attempt) + random(0, jitter)
# Prefer "full jitter": sleep = random(0, min(cap, base * 2^attempt))
DashNote · Partial
LLM/embeddings use tenacity wait_exponential with retryable vs fatal splits (src/shared/llm/retry.py. Gap: no wait_random_exponential / jitter yet. Workers re-raise retryable embed failures for ARQ.

09 Circuit breakers

After N failures, open the circuit: fail fast instead of waiting on a dead dependency. After a cooldown, try half-open with a probe request; success → close.

Closed→ failures Open→ cooldown Half-open→ ok? Closed
  • Pair with timeouts — a breaker without timeouts still waits forever on each try.
  • Scope per dependency (LLM vs Qdrant vs Stripe), not one global breaker.
  • When open: degrade (cached answer, skip feature) instead of 500 storms.
DashNote · Gap
No pybreaker / similar around LiteLLM or Qdrant. Failures retry-until-exhaust or degrade via flags. Should be: breaker after retry exhaustion on LLM + Qdrant; surface degraded mode in metrics.

10 Bulkheads

Ship compartments: a flood in one hold doesn’t sink the ship. Limit concurrency / pool size per dependency so LLM timeouts can’t exhaust the DB pool.

Process bulkhead

API vs worker containers — DashNote already separates them.

Pool / semaphore

Cap concurrent outbound LLM calls; separate DB pool sizes.

Queue bulkhead

WORKER_MAX_JOBS caps fan-in — a soft TPM bulkhead.

DashNote · Partial
API ≠ worker processes; WORKER_MAX_JOBS; event bus drops if Redis down (HTTP isolated). Missing: per-dependency async semaphores for LLM vs Qdrant vs DB.

11 Graceful degradation

When a dependency dies, serve a worse but useful experience — don’t blue-screen the whole product.

Core CRUD→ Chat OK→ Agent / Qdrant optional→ 503 only on AI routes
  • Fail-open vs fail-closed is a product decision (rate limit fail-open = availability; auth fail-closed = safety).
  • Feature flags / ai_enabled gates keep core notes usable.
  • Never block the write path on secondary indexes.
DashNote · Covered
Strong ladder in src/main.py lifespan: Qdrant bootstrap fail → API boots; checkpointer fail → agent degraded; Redis missing → rate limit fail-open + cache miss + JWT stateless; events dropped, HTTP continues. Teaching gold.

12 Health checks — liveness vs readiness

Orchestrators need two different answers. Mixing them causes restart loops or traffic to sick pods.

ProbeQuestionIf failShould check
Liveness Is the process stuck / deadlocked? Restart the container Process up — not deep deps
Readiness Can I take traffic right now? Remove from LB DB (+ Redis if required for this instance)
Startup Finished booting? Wait / fail start Migrations, warm pools
Anti-pattern
Using deep /health (DB+Redis) as the only Compose/k8s probe: a Redis blip restarts healthy API workers. Split /live and /ready.
DashNote · Partial
GET /health in src/core/health.py checks DB + Redis → 503 if either down. Qdrant intentionally excluded. Prod Compose healthcheck hits this deep endpoint. Should be: /live = process; /ready = DB (+ Redis if required); optional /health/ai for Qdrant.

13 Idempotent handlers — the #1 habit

Networks retry. Clients double-click. Workers redeliver. If your handler isn’t idempotent, retries create duplicates. Design so “do it twice” = “do it once.”

Natural idempotency

  • PUT / overwrite by ID
  • Upsert with deterministic key
  • ON CONFLICT DO NOTHING

Explicit key

  • Idempotency-Key header
  • Store key → response for TTL
  • Same key + same body → same result
Distributed-systems habit
Assume every message and every POST may arrive twice. Prefer upserts and unique constraints over “hope the network is nice.”
DashNote · Covered
Deterministic chunk UUIDs → Qdrant upsert (chunker.py); note–file ON CONFLICT DO NOTHING; indexing request_id for tracing. Gap: HTTP Idempotency-Key for create POSTs; ARQ job-id dedupe table where side effects aren’t upsert-safe.

1. Liveness vs readiness

Probes · split deep health 
# FastAPI — should-be upgrade over single /health
@router.get("/live")
async def live():
    return {"status": "alive"}

@router.get("/ready")
async def ready(response: Response, db: AsyncSession = Depends(get_db)):
    try:
        await db.execute(text("SELECT 1"))
        return {"status": "ready", "database": True}
    except Exception:
        response.status_code = 503
        return {"status": "not_ready", "database": False}
// NestJS + @nestjs/terminus
@Get("live")
@HealthCheck()
live() {
  return this.health.check([]); // process up
}

@Get("ready")
@HealthCheck()
ready() {
  return this.health.check([
    () => this.db.pingCheck("database"),
    // () => this.redis.pingCheck("redis"), // if required
  ]);
}

2. Retries with full jitter

Transient only · exponential + jitter 
# FastAPI / tenacity — DashNote uses wait_exponential; prefer jitter
from tenacity import (
    retry, retry_if_exception_type, stop_after_attempt,
    wait_random_exponential,
)

@retry(
    stop=stop_after_attempt(5),
    wait=wait_random_exponential(multiplier=1, max=20),
    retry=retry_if_exception_type(RETRYABLE_EXCEPTIONS),
    reraise=True,
)
async def call_llm(**kwargs):
    return await litellm.acompletion(**kwargs)
// NestJS — axios-retry or custom backoff
async function withJitter<T>(fn: () => Promise<T>, attempts = 5) {
  let last: unknown;
  for (let i = 0; i < attempts; i++) {
    try { return await fn(); }
    catch (e) {
      last = e;
      if (!isRetryable(e) || i === attempts - 1) throw e;
      const cap = Math.min(20_000, 1000 * 2 ** i);
      await sleep(Math.random() * cap); // full jitter
    }
  }
  throw last;
}

3. Circuit breaker (sketch)

Fail fast when dependency is down 
# FastAPI — pybreaker-style sketch (not in repo yet)
class Breaker:
    def __init__(self, fail_max=5, reset_timeout=30):
        self.fail_max, self.reset_timeout = fail_max, reset_timeout
        self.failures, self.opened_at, self.state = 0, 0.0, "closed"

    async def call(self, fn):
        if self.state == "open":
            if time.monotonic() - self.opened_at < self.reset_timeout:
                raise RuntimeError("circuit open")
            self.state = "half_open"
        try:
            result = await fn()
            self.failures, self.state = 0, "closed"
            return result
        except Exception:
            self.failures += 1
            if self.failures >= self.fail_max:
                self.state, self.opened_at = "open", time.monotonic()
            raise

llm_breaker = Breaker()
# await llm_breaker.call(lambda: litellm.acompletion(...))
// NestJS — opossum
import CircuitBreaker from "opossum";

const breaker = new CircuitBreaker(
  (payload: object) => this.llm.complete(payload),
  { timeout: 10_000, errorThresholdPercentage: 50, resetTimeout: 30_000 },
);
breaker.fallback(() => ({ degraded: true, text: "AI temporarily unavailable" }));

return breaker.fire({ messages });

4. Idempotency-Key middleware

POST create · store response by key 
# FastAPI — Redis-backed idempotency for creates
async def create_note(body, redis, key: str | None = Header(None, alias="Idempotency-Key")):
    if key:
        cached = await redis.get(f"idem:{key}")
        if cached:
            return JSONResponse(content=json.loads(cached))
    note = await repo.create(body)
    payload = NoteOut.model_validate(note).model_dump()
    if key:
        await redis.set(f"idem:{key}", json.dumps(payload), ex=86400)
    return payload
// NestJS — interceptor / guard pattern
@Post()
async create(
  @Body() body: CreateNoteDto,
  @Headers("idempotency-key") key?: string,
) {
  if (key) {
    const hit = await this.redis.get(`idem:${key}`);
    if (hit) return JSON.parse(hit);
  }
  const note = await this.notes.create(body);
  if (key) {
    await this.redis.set(`idem:${key}`, JSON.stringify(note), "EX", 86400);
  }
  return note;
}

16 Mastery checklist

Scalability

  • Explain vertical vs horizontal with a DB vs API example
  • Design a stateless API (JWT + shared Redis) without sticky sessions
  • Sketch LB + readiness routing + drain on deploy
  • Say when read replicas help — and what lag breaks
  • Name what you’d shard by (and what you’d try first instead)
  • Apply CAP/PACELC per operation, not “the whole system”

Reliability

  • Set timeout budgets (outer > inner)
  • Retry only transients with full jitter
  • Draw closed → open → half-open for a breaker
  • Isolate a dependency with a bulkhead / semaphore
  • Separate /live and /ready and justify each
  • Make a POST idempotent (upsert or Idempotency-Key)

DashNote gaps

  • Split /live vs /ready
  • Multi-replica API behind Nginx
  • Jitter on LLM retries
  • Circuit breaker for LLM / Qdrant
  • HTTP Idempotency-Key on creates
