Caching

How to make systems faster without lying about truth — strategies, TTL, stampedes, Redis patterns, and the difference between CDN, app cache, and the DB buffer pool.

Full curriculum Redis-first FastAPI · NestJS

00 Overview

A cache stores answers you already paid to compute — so the next request is cheaper. Every cache introduces a consistency problem: stale data vs origin load.

What this book covers
  1. Layers: CDN · app (Redis) · DB buffer pool
  2. Strategies: aside, through, behind, refresh-ahead
  3. TTL, eviction, stampede / thundering herd
  4. Redis: sessions, rate limits, locks (and why locks bite)
  5. Invalidation, key design, what not to cache
Request→ CDN?→ App + Redis→ DB (+ buffer pool)
DashNote
App-level Redis cache-aside for notes/notebooks + embedding cache; Redis for JWT refresh/blacklist and rate limits. No CDN / Nginx proxy_cache. Postgres uses its own buffer pool (untuned in-app).

01 Cache layers — CDN vs app vs DB

These are not interchangeable. Wrong layer = wrong invalidation story.

LayerWhat it cachesWho controls TTLGood for
CDN / edge HTTP responses, static assets Cache-Control, purge API Public pages, images, JS; geo latency
App cache (Redis) JSON blobs, computed results, tokens Your code Hot API reads, expensive compute, shared state
Local / process In-memory LRU Process lifetime Tiny hot config; dangerous with many replicas
DB buffer pool Table/index pages in RAM DB engine (e.g. Postgres shared_buffers) Repeated queries over working set — not an app API
ORM / query cache Identity map / query results Session/request Avoid re-fetch in one request — not cross-request

CDN

Cache HTTP. Must be safe for shared caches (public vs private). Auth APIs rarely belong here.

App Redis

Cache domain objects. Tenant keys, auth-aware variants, explicit invalidation.

DB buffer

Cache disk pages. You “use” it by having a hot working set and good indexes — not by SET/GET.

Guideline
Don’t “add Redis” to fix a missing index. Fix the query plan first; then cache the expensive result.
DashNote · Partial
Covered: Redis app cache. Gap: CDN / edge HTTP cache. Aware: DB buffer pool exists under Postgres but isn’t an app config surface here (only SQLAlchemy pool_pre_ping — connection pool ≠ buffer pool).

02 Caching strategies

Cache-aside (lazy loading)

  1. Read cache → hit? return
  2. Miss → load from DB → write cache → return
  3. On write: update DB, then invalidate (or bump generation)

Most common for APIs. App owns consistency. Simple; stampede risk on hot keys.

Write-through

Write hits cache and DB together (cache library or dual write). Reads always from cache. Stronger freshness; slower writes; need failure handling if one side fails.

Write-behind (write-back)

Write to cache, flush to DB async. Fast writes; risk of data loss on crash; hard ops. Rare for primary truth.

Refresh-ahead

Refresh before TTL expiry for predictable hot keys. Reduces miss storms; wastes work if key goes cold.

StrategyRead pathWrite pathPick when
Cache-aside App checks cache DB then invalidate Default for CRUD APIs
Write-through Cache Cache + DB sync Read-heavy, write must stay warm
Write-behind Cache Cache → async DB Extreme write volume + durable queue
DashNote · Covered (aside)
WorkspaceRedisCache.aside_json — miss loads DB, setex with TTL. Mutations bump_generation (INCR) so old keys become unreachable without SCAN. Write-through / write-behind: not used.

03 TTL & eviction

TTL is a safety net; invalidation is the precision tool.

  • Short TTL (seconds–minutes) — lists, permissions-ish data, “good enough” freshness
  • Long TTL (hours–days) — pure functions of input (embeddings of text), public config
  • No TTL — dangerous unless you have hard invalidation + memory policy
  • Jitter — randomize TTL slightly so keys don’t expire in sync (herd)

Eviction policies (Redis)

  • volatile-lru / allkeys-lru — drop least recently used
  • volatile-ttl — expire soonest first among TTL keys
  • noeviction — writes fail when full (fail loud)
Guideline
TTL alone ≠ correctness. After a write, invalidate (or version) so users don’t stare at stale data for the full TTL.
DashNote
CACHE_TTL_SECONDS=60 for workspace JSON; EMBEDDING_CACHE_TTL=86400 for vectors; refresh tokens / blacklist use JWT lifetime; rate-limit keys expire window*2. Generation counters have no TTL (monotonic INCR until flush).

04 Cache stampede & thundering herd

When a hot key expires (or is invalidated), many concurrent requests miss at once and all hammer the origin — that’s a stampede / thundering herd.

Defenses

Singleflight / request coalescing

One request fills the cache; others wait on the same future.

Lock around fill

SET key:lock NX EX — winner loads DB; losers retry/sleep or serve stale.

Probabilistic early expiration

XFetch-style: refresh before hard TTL based on remaining time + random.

Serve stale

Keep soft-expired value; one refresher updates; others get stale-while-revalidate.

Also causes herds
Mass invalidation (flushall, bumping a global version, deploy cache wipe) + traffic spike. Prefer per-tenant / per-domain generations over global flush.
DashNote · Gap
aside_json is naive get→load→set. Concurrent misses all hit Postgres. Generation bump is good for invalidation scale, but a popular list key after bump can still stampede. Should be: singleflight or lock-around-fill on hottest keys.

05 Key design & invalidation

  • Include tenant, resource, variant (role/user), version/gen
  • Never put secrets in keys; be careful with PII in key material
  • Prefer version/generation counters over SCAN + delete
  • Document who owns invalidation on each write path
# DashNote-style keying
app:cache:w:{workspace_id}:notes:list:{gen}:{staff|u{user_id}}
app:cache:gen:notes:{workspace_id}   # INCR to invalidate all list/detail variants
embed:v1:{sha256(text)}
DashNote · Covered
Tenant-rooted keys + RBAC list variants + generation bump on note/notebook writes. See src/core/redis/cache.py, notes/notebooks routers.

06 Redis for sessions & tokens

Server sessions

Store session id → user blob in Redis; cookie holds opaque id. Easy revoke; sticky less needed.

JWT + Redis state

JWT is self-contained; Redis tracks refresh jti, rotation, access blacklist. Hybrid model.

  • TTL = session/refresh lifetime
  • Rotate refresh tokens; bind to user id
  • Logout = delete refresh + blacklist access until exp
DashNote · Covered
Not classic cookie sessions — RedisTokenStore: refresh keys + access blacklist. Fail-open to no-op store when Redis disabled (dev convenience; prod should require Redis for auth state).

07 Redis rate limits

Redis is a natural shared counter for multi-instance APIs.

  • Fixed window — simple INCR + EXPIRE; burst at window edges
  • Sliding window — fairer; ZSET or two-window approx
  • Token bucket — smooth rate; Lua or Redis cell modules
Design choice
Fail-open (allow if Redis down) protects availability; fail-closed protects abuse. Document which you picked — DashNote fails open.
DashNote · Covered
App: fixed window 100/min global + 5/min login via Redis. Edge: Nginx limit_req 10r/s (not Redis). Dual layer is intentional.

08 Distributed locks — and their dangers

Locks coordinate; they do not create correctness by themselves.

Basic Redis lock

SET lock:job:42 <token> NX EX 30
# do work
# delete only if token matches (Lua) — never DEL blindly

Dangers

  • Lock expiry while work runs — two workers both “hold” the lock
  • Clock / GC pauses — Redlock debates; prefer fencing tokens for safety-critical work
  • Deadlock — forgotten unlock; always TTL
  • Using locks instead of DB constraints — races still win; UNIQUE is stronger
  • Locking the world — coarse locks kill throughput
Guideline
Prefer idempotent upserts + unique constraints for correctness. Use locks for “only one refresher fills this cache key” or “only one worker runs this cron” — not for money without fencing + careful design.
DashNote · Gap
No Redis distributed locks. In-process locks only for client factories. Stampede protection would be the first honest lock use-case.

10 Consistency models

  • Eventual — TTL or async invalidation; users may see old data briefly
  • Read-your-writes — after mutate, read primary or bust your own cache key
  • Strong via write-through — still fails if replicas lag
Classic bug
Update DB, then fail to invalidate → stale until TTL. Always invalidate in the same code path as commit (and accept rare races, or use versions).

11 What to cache (and what not)

Cache

  • Hot read-mostly lists/details
  • Expensive pure compute (embeddings)
  • Rate-limit / ephemeral auth state
  • Feature flags / config with short TTL

Don’t cache (naively)

  • Per-request highly personalized without key variants
  • Secrets / raw credentials
  • Data you can’t invalidate on write
  • Tiny queries already served by DB buffer + index

12 Observability

  • Hit ratio (per key prefix / domain)
  • Miss latency vs hit latency
  • Redis memory, evictions, CPU
  • Origin QPS after deploys / invalidation storms
  • Error rate when Redis down (fail-open vs closed)

14 Code examples TOGGLE

FastAPI/redis-py matches DashNote. NestJS uses ioredis parallels.

1. Cache-aside + generation bump

Read path · invalidate on write 
# FastAPI — mirrors WorkspaceRedisCache
async def aside_json(redis, key: str, ttl: int, loader):
    raw = await redis.get(key)
    if raw is not None:
        return json.loads(raw)
    value = await loader()
    await redis.setex(key, ttl, json.dumps(value))
    return value

# read
gen = await redis.get(f"app:cache:gen:notes:{wid}") or "0"
key = f"app:cache:w:{wid}:notes:list:{gen}:staff"
notes = await aside_json(redis, key, 60, load_notes_from_db)

# write — DB commit then:
await redis.incr(f"app:cache:gen:notes:{wid}")
// NestJS + ioredis
async asideJson<T>(key: string, ttl: number, loader: () => Promise<T>): Promise<T> {
  const raw = await this.redis.get(key);
  if (raw) return JSON.parse(raw) as T;
  const value = await loader();
  await this.redis.setex(key, ttl, JSON.stringify(value));
  return value;
}

// invalidate
await this.redis.incr(`app:cache:gen:notes:${workspaceId}`);

2. Stampede protection (lock around fill)

Should-be for hot keys 
# Single-flight via Redis lock (simplified)
async def aside_with_lock(redis, key: str, ttl: int, loader):
    raw = await redis.get(key)
    if raw is not None:
        return json.loads(raw)

    token = str(uuid4())
    got = await redis.set(f"{key}:lock", token, nx=True, ex=5)
    if got:
        try:
            value = await loader()
            await redis.setex(key, ttl, json.dumps(value))
            return value
        finally:
            # delete only if we own the lock (use Lua in prod)
            if await redis.get(f"{key}:lock") == token:
                await redis.delete(f"{key}:lock")
    # loser: brief wait then re-get (or return stale if you keep one)
    await asyncio.sleep(0.05)
    raw = await redis.get(key)
    return json.loads(raw) if raw else await loader()
// NestJS — SET NX EX then fill
async asideWithLock<T>(key: string, ttl: number, loader: () => Promise<T>): Promise<T> {
  const hit = await this.redis.get(key);
  if (hit) return JSON.parse(hit);

  const token = randomUUID();
  const got = await this.redis.set(`${key}:lock`, token, 'EX', 5, 'NX');
  if (got === 'OK') {
    try {
      const value = await loader();
      await this.redis.setex(key, ttl, JSON.stringify(value));
      return value;
    } finally {
      // Lua compare-and-del in production
      await this.redis.del(`${key}:lock`);
    }
  }
  await new Promise((r) => setTimeout(r, 50));
  const again = await this.redis.get(key);
  return again ? JSON.parse(again) : loader();
}

3. Rate limit (fixed window)

Shared counter 
# FastAPI — DashNote-style fixed window
async def allow(redis, scope: str, identity: str, limit: int, window: int) -> bool:
    if redis is None:
        return True  # fail-open (DashNote)
    bucket = int(time.time()) // window
    key = f"rate_limit:{scope}:{identity}:{bucket}"
    n = await redis.incr(key)
    if n == 1:
        await redis.expire(key, window * 2)
    return n <= limit
// NestJS
async allow(scope: string, identity: string, limit: number, window: number) {
  if (!this.redis) return true; // fail-open
  const bucket = Math.floor(Date.now() / 1000 / window);
  const key = `rate_limit:${scope}:${identity}:${bucket}`;
  const n = await this.redis.incr(key);
  if (n === 1) await this.redis.expire(key, window * 2);
  return n <= limit;
}
