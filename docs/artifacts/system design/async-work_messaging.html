Async work & messaging

Queues, workers, and delivery semantics — when to leave the HTTP request, how retries and poison messages work, and the practical truth about “exactly-once.”

Full curriculum ARQ · Redis FastAPI · NestJS

00 Overview

Sync HTTP is great until work is slow, flaky, or multi-step. Async systems move that work to workers behind a durable queue — trading immediacy for reliability and scale.

What this book covers
  1. When background jobs beat long HTTP
  2. Queues vs pub/sub
  3. At-least-once vs exactly-once (practical truth)
  4. Workers, retries/backoff, DLQ, poison messages
  5. Idempotency, outbox, job visibility
API→ Enqueue→ Redis / broker→ Worker→ Side effects
DashNote shape
FastAPI enqueues ARQ jobs on Redis (arq_pool). Worker process runs embed / file parse / tags / metadata. “Event bus” = typed events → task name map, not Redis pub/sub. Chat/agent stay on the request (SSE).

01 When background jobs beat long HTTP

Go async when

  • Work often exceeds ~1–2s (or has heavy tail)
  • Calls flaky externals (LLM, OCR, email)
  • You need retries without holding the client
  • Fan-out: one upload → extract + embed + tag
  • Client doesn’t need the result to finish the UX

Stay sync when

  • User must see the result to continue
  • Work is cheap and reliable (< hundreds of ms)
  • Failure must fail the HTTP transaction visibly
  • Streaming the result is the product (SSE chat)
Guideline
Return the domain resource immediately (note created, file uploaded). Run indexing/enrichment in the background. Tell the client how to know when it’s ready (poll field, 202+job, webhook, or “search catches up”).
DashNote · Covered
Note create returns NoteRead then enqueues embed (+ tags via event). File upload returns file then FileUploadedEvent → parse → fan-out. Enqueue failures are logged — HTTP still succeeds (search may lag). Agent/RAG remain request-scoped (correct for interactive latency).

02 Queues vs pub/sub

Work queuePub/Sub
Intent Do this job (competing consumers) Announce this happened (fan-out)
Consumers One worker processes each message All subscribers get a copy (or none if offline)
Persistence Usually durable until ack Classic pub/sub is fire-and-forget
Examples ARQ, Celery, SQS, Rabbit work queues, BullMQ Redis Pub/Sub, SNS, Kafka fan-out topics*
Use for Embed, email, OCR, billing settle Live UI updates, cache bust signals, many independent reactors

*Kafka / streams blur the line: durable log + consumer groups ≈ queue semantics per group, pub/sub across groups. Start with “queue for work, stream/bus for events.”

DashNote · Covered (queues)
ARQ Redis list / BLPOP work queue. Domain “events” are enqueued as jobs via emit_event — not Redis Pub/Sub. Fan-out = worker enqueues more jobs.

03 Delivery guarantees — practical truth

GuaranteeMeaningReality
At-most-once May lose messages; never duplicates Rarely OK for money/email; OK for metrics
At-least-once May duplicate; won’t silently lose if durable Default for serious systems
Exactly-once Process once end-to-end Marketing term — usually “effectively once” via idempotency + txn
Practical truth
Brokers give at-least-once. You get exactly-once effects by making handlers idempotent (upserts, unique constraints, dedupe keys) — not by believing a checkbox.
DashNote · Partial
At-least-once via ARQ retries. Soft idempotency: deterministic chunk IDs + Qdrant upsert. No job-id dedupe on enqueue → double-click / double-emit can queue duplicates.

04 Workers

  • Separate process(es) that pull jobs and run handlers
  • Scale horizontally: more workers → higher throughput (watch DB/API quotas)
  • Concurrency: max_jobs / worker pool size — don’t exceed downstream limits
  • Timeouts: kill runaway jobs; don’t leave zombies holding locks
  • Isolate heavy CPU (parse) from I/O-bound (LLM) pools when needed
DashNote · Covered
python -m arq src.worker.main.WorkerSettings in Compose. WORKER_MAX_JOBS (default 5), job_timeout=300, keep_result=3600. Tasks: embed note, file uploaded pipeline, tags, metadata, chunk indexing.

05 Retries & backoff

  • Retry transient failures (429, 503, timeouts, network blips)
  • Don’t retry permanent 400s / validation / “not found” after confirm
  • Exponential backoff + jitter — avoid synchronized stampedes
  • Cap max_tries; then DLQ or mark failed
  • Distinguish task-level retry (ARQ) vs library retry (Tenacity around LLM)
DashNote · Partial
LLM/embed paths use Tenacity exponential backoff. Workers re-raise retryable errors; fatal → log + return. No explicit ARQ max_tries override / DLQ yet.

06 Dead-letter queues & poison messages

A poison message always fails (bad payload, bug, missing dependency). Without a DLQ it blocks the queue or retries forever.

  1. After N failures → move to dead-letter queue / table
  2. Alert on DLQ depth
  3. Inspect, fix code or data, replay or discard
  4. Never infinite-retry poison without a circuit

Backoff

Space retries so the system can recover (deps, rate limits).

DLQ

Park poison so healthy jobs keep flowing; humans/tools replay later.

DashNote · Gap
No dead-letter queue or poison parking. Failed fatals are logged. Should be: max tries → DLQ list/table + alert + replay tool.

07 Idempotent handlers

Assume every job may run twice. Design effects that converge.

  • Upsert by natural key (chunk id, email send id)
  • Unique constraints + catch conflict
  • Store processed_job_id / event id before side effects (or in same txn as outbox)
  • Avoid “increment counter” without idempotency keys
DashNote · Partial
Qdrant upsert with stable uuid5(note_id:index) chunk ids — re-run safe for embeds. Note create still fires two jobs (embed + tags) by design — both should stay idempotent.

08 Common patterns

Fire-and-forget

Enqueue after commit; return 200. Client doesn’t wait. DashNote default.

202 + job status

Return job id; client polls /jobs/{id} until terminal.

Saga / choreography

Event → workers → more events. Need compensations for failures.

  • Fan-out — one event triggers many jobs (file → index + metadata)
  • Delayed / scheduled — run_at, cron workers
  • Priority queues — interactive vs batch

09 Outbox & ordering

Dual-write problem: commit DB then enqueue — process can crash between them (lost event) or enqueue then fail DB (orphan job). Transactional outbox: write row + outbox in one DB txn; relay publishes to the broker.

  • Ordering: single queue ≠ global order; use partition keys when order matters
  • Prefer causal order per aggregate (note_id) over total order
DashNote · Gap (outbox)
Commit then best-effort enqueue (never blocks HTTP). Rare lost jobs if Redis blips after commit. Acceptable early; outbox is the production hardening step.

10 Job visibility for clients

  • Poll resource fields (indexed_at, tags populated)
  • Job API: queued → running → succeeded/failed
  • Push: websocket / SSE progress / webhook
DashNote · Gap
No 202 / job-id API. ARQ keep_result unused by clients. UX relies on eventual search/tags. Should be: indexing status on note/file or jobs endpoint.

1. Fire-and-forget after commit

Don’t block HTTP 
# FastAPI + ARQ — DashNote notes pattern
@router.post("/", response_model=NoteRead)
async def create_note(data: NoteCreate, request: Request, ctx = Depends(...), db = Depends(...)):
    note = await repo.create(...)
    await db.commit()

    try:
        await request.app.state.arq_pool.enqueue_job(
            "embed_note_task",
            request_dict=IndexingRequest(...).model_dump(),
        )
    except Exception:
        logger.warning("Failed to enqueue embedding", extra={"note_id": note.id})
        # still return success — indexing is best-effort

    return note
// NestJS + BullMQ
@Post()
async create(@Body() dto: CreateNoteDto, @Req() req) {
  const note = await this.notes.create(dto);
  await this.embedQueue.add(
    'embed_note',
    { noteId: note.id, workspaceId: req.user.workspaceId },
    { attempts: 5, backoff: { type: 'exponential', delay: 2000 },
      removeOnComplete: true },
  ).catch((e) => this.logger.warn('enqueue failed', e));
  return note; // 201 — client not waiting for embed
}

2. Event → task map (lightweight bus)

Domain event dispatch 
# shared/events/bus.py style — never raise into HTTP
_TASK_MAP = {
    "file.uploaded": "handle_file_uploaded",
    "note.created": "handle_note_created",
}

async def emit_event(event, arq_pool) -> bool:
    if arq_pool is None:
        logger.warning("no arq_pool — event dropped")
        return False
    task = _TASK_MAP.get(event.event_type.value)
    if not task:
        return False
    try:
        await arq_pool.enqueue_job(task, event_data=event.model_dump(mode="json"))
        return True
    except Exception:
        logger.exception("emit_event failed")
        return False
// NestJS — EventEmitter → queue (or @OnEvent handlers that enqueue)
async emit(event: DomainEvent) {
  const task = TASK_MAP[event.type];
  if (!task) return false;
  try {
    await this.queue.add(task, event.payload, {
      jobId: `${event.type}:${event.id}`, // dedupe
      attempts: 5,
      backoff: { type: 'exponential', delay: 2000 },
    });
    return true;
  } catch (e) {
    this.logger.error('emit failed', e);
    return false;
  }
}

3. Idempotent worker + retry classification

Safe under at-least-once 
# ARQ task — upsert is safe to retry
async def embed_note_task(ctx, request_dict: dict):
    req = IndexingRequest.model_validate(request_dict)
    try:
        chunks = chunk_note(req)  # stable uuid5 ids
        await qdrant.upsert(chunks)  # idempotent
    except TransientLLMError:
        raise  # ARQ retries
    except PermanentError as e:
        logger.error("fatal embed", extra={"error": str(e)})
        return {"ok": False}  # stop retrying
// BullMQ processor
@Processor('embed')
export class EmbedProcessor {
  @Process('embed_note')
  async handle(job: Job) {
    try {
      const chunks = chunkNote(job.data); // stable ids
      await this.qdrant.upsert(chunks);
    } catch (e) {
      if (isTransient(e)) throw e; // retry
      this.logger.error('fatal', e);
      // don't throw → job completes failed without infinite retry
      // or: move to DLQ queue explicitly
    }
  }
}
