Storage & Database Scaling

Pick the right store for the access pattern — then grow Postgres without downtime. Blobs, signed URLs, hot/cold tiers, pooling, replicas, shards, and expand→dual-write→contract.

Full curriculum Architect + backend FastAPI · NestJS

00 Overview

Storage choice is an access-pattern decision, not a fashion decision. Database scaling is what you do when one primary still owns the truth — but traffic, size, or deploys outgrow “just ALTER TABLE.”

What this book covers
  1. SQL vs document vs key-value vs wide-column — when each wins
  2. Object storage + signed URLs for files
  3. Hot vs cold data; backup/restore as a design req
  4. Pooling, read replicas, lag
  5. Partitioning / sharding keys and hotspots
  6. Migrations without downtime (expand → dual-write → contract)
Postgresmeta Object storeblobs RedisKV / queue Qdrantvectors
DashNote today
Postgres 16 (source of truth) + Redis (cache/auth/ARQ) + pluggable blobs (local / MinIO / R2) + Qdrant (embeddings). Logical tenancy via workspace_id. No read replicas, no PITR runbook, pooling mostly defaults.

Part 10 · Storage choices

01 SQL · document · KV · wide-column

Four families. Same bytes on disk; different query contracts.

SQL (relational)

Tables, joins, transactions, schemas. Postgres, MySQL.

Document

JSON docs, flexible fields, denormalized reads. Mongo, Firestore.

Key-value

Get/set by key, tiny latency. Redis, DynamoDB (simple), etcd.

Wide-column

Row key + sparse columns, huge write/scan. Cassandra, Bigtable, Scylla.

FamilyStrengthWeaknessClassic fit
SQL Integrity, joins, ad-hoc queries, ACID Horizontal scale is hard; schema changes careful Users, billing, notes, memberships
Document Flexible payloads; whole-entity reads Joins awkward; easy to duplicate inconsistently CMS pages, product catalogs, event payloads
Key-value Speed; simple ops; TTL; queues No rich query; you design the key Sessions, cache, rate limits, job brokers
Wide-column Massive write throughput; time-series scans Query model rigid; ops heavy Metrics, IoT, activity feeds at extreme scale
Postgres cheat
JSONB + GIN indexes lets you store “document-ish” fields inside SQL without a second DB. DashNote does this for tags / citations / extracted metadata.
DashNote · Covered (polyglot, intentional)
SQL primary · Redis as KV · Qdrant as vector specialty store · no Mongo / Cassandra. Neo4j appears only as an env stub — not in the runtime path.

02 When to pick what

Start from the question you ask most often — not from the vendor logo.

If you need…PreferAvoid defaulting to
Multi-entity consistency (user + workspace + membership) SQL + transactions Two document collections + hope
Lookup by ID / TTL / counters Redis (KV) Postgres for every cache hit
Binary files (PDF, images) Object storage BYTEA / base64 in SQL rows
Semantic search / embeddings Vector DB (Qdrant) or pgvector LIKE '%query%' at scale
Billions of append-only events Wide-column / OLAP / stream One fat OLTP table forever
Rule
One source of truth per domain fact. Cache and search indexes are derived — rebuildable. Don’t invent a second writer for the same money/permission row.

03 Object / blob storage & signed URLs

Blobs are large, opaque, and rarely queried by content in SQL. Put them in S3-compatible storage; keep metadata (owner, size, mime, key) in Postgres.

Client→ API upload→ Object store+ File row (key)→ Presigned GET

Signed (presigned) URLs

  • API never streams every download through itself (saves bandwidth & RAM).
  • URL embeds short-lived auth for one object — no public bucket.
  • Expiry is a security control (minutes–hours), not “forever share.”
  • Local/dev backends often return an app download path instead.

Store in blob

  • PDFs, images, attachments
  • Exports, backups, model artifacts

Keep in DB

  • storage_key, mime, size, workspace
  • Permissions / soft-delete flags
DashNote · Covered (dev) · Partial (prod ops)
Backends: local | minio | r2 via src/core/storage/client.py. Upload → generate_storage_key(workspace_id, …) → persist File → emit event. Presigned GET for S3 backends; local falls back to /files/{id}/download. Should be: prod STORAGE_BACKEND=r2 (no shared volume); finish storage deploy docs.

04 Hot vs cold data

Hot data is touched often and needs low latency. Cold data is rarely read — optimize for cost and retention, not milliseconds.

TierExamplesStorePolicy
Hot Active notes, sessions, recent lists Postgres + Redis cache Indexes, short TTL caches
Warm Older notes still searchable Postgres + Qdrant Keep queryable; watch size
Cold Deleted exports, old audit logs, unused blobs Object archive / Glacier-class Lifecycle rules; restore = hours OK
Design early
Decide retention per class: DB rows, blobs, vectors, traces. Soft-delete without a purge job is just “hot forever with a flag.”
DashNote · Gap
Embeddings in Qdrant; extracted_text stays in Postgres; embedding Redis TTL 24h. SoftDeleteMixin exists but unused. No archive/retention for notes/files/vectors. Should be: retention policy + lifecycle on R2; purge/archive jobs later.

05 Backup / restore as a design requirement

A backup you never restore is fiction. Design the restore path — RPO (how much loss), RTO (how long to recover) — before you need them.

What to back up

  • Postgres (PITR / snapshots)
  • Object store (versioning)
  • Qdrant snapshots (or rebuild from source)

What is rebuildable

  • Redis cache / rate limits
  • ARQ job queue (usually)
  • Derived search indexes

Restore drill

  • Quarterly: restore to staging
  • Time it → update RTO
  • Document who runs it
Compose volumes ≠ backup
Named Docker volumes survive compose down — they do not survive disk loss. Hosted Postgres PITR + object versioning are the real plan.
DashNote · Gap
Volumes: postgres_data, qdrant_data, local_storage. No pg_dump scripts, PITR docs, or restore drill. Should be: vendor PITR (e.g. Supabase) + R2 versioning + Qdrant Cloud snapshots; one-page restore runbook.

Part 12 · Database scaling basics

06 Connection pooling

Opening a Postgres connection is expensive. A pool reuses connections. Too many clients × too many pool slots = “too many connections” and meltdown.

LayerRoleNotes
App pool (SQLAlchemy / TypeORM) Per process pool_size, max_overflow, pool_recycle, pool_pre_ping
External pooler (PgBouncer / Supabase) Many apps → few DB conns Transaction mode: no session features across requests
Migrations One-shot Use NullPool — don’t hold idle pool during migrate
Math
Rough ceiling: replicas × workers × pool_size must stay under max_connections (minus admin headroom). Prefer a transaction pooler in prod.
DashNote · Partial
create_async_engine(..., pool_pre_ping=True) only — no explicit size/overflow. Alembic uses NullPool. Separate LangGraph checkpointer pool exists. Prod docs mention Supabase pooler :6543. Should be: set pool knobs; always use pooler URL in prod API.

07 Read replicas & lag

Replicas copy from the primary asynchronously. You buy read QPS — you pay with replication lag (milliseconds to seconds).

Primary

  • All writes
  • Read-your-writes (just created)
  • Auth / money / locks

Replica

  • List / search / reports
  • Analytics tolerating lag
  • Offload heavy SELECTs
  • Lag is normal. “Stale list for 200ms” ≠ bug; “missing my new note” is.
  • Monitor lag; alert when it exceeds your product SLA.
  • Failover promotes a replica — plan for brief write unavailability.
DashNote · Gap
Single DATABASE_URL. No DATABASE_READ_URL or routing. Async Qdrant indexing already teaches “eventual read” for search — same mental model as replica lag for SQL lists.

08 Partitioning / sharding keys & hotspots

Partitioning splits one table inside one database (by range/list/hash). Sharding splits across many databases. Both need a key — and a bad key creates hotspots.

Good key

workspace_id — related rows stay together; queries are tenant-scoped.

Hotspot

One huge workspace, or a global sequential key every write hits (status=active).

Before shards

Indexes → cache → replicas → table partitions → then physical shards.

Hotspot patterns

  • Celebrity tenant — one workspace owns 80% of rows/QPS → cache aggressively; consider dedicated shard.
  • Monotonic ID write — all inserts hit the newest B-tree leaf → use UUIDv7 / hash if needed.
  • Global counter row — everyone updates one row → use Redis INCR or sharded counters.
DashNote · Covered (logical) · Gap (physical)
Tenancy via WorkspaceTenantMixin.workspace_id + tenant_filter — correct future shard key. No PARTITION BY, no shard router. Files have composite indexes; notes list may want (workspace_id, created_at DESC).

09 Migrations without downtime

Online schema change rule: never make the running app and the new schema incompatible in one step. Use expand → dual-write → contract.

1 Expand→ 2 Dual-write / backfill→ 3 Switch reads→ 4 Contract
PhaseWhat you doApp version
Expand Add new column/table (nullable or with default). Old code ignores it. vN still deployed
Dual-write App writes old + new. Backfill historical rows in batches. vN+1
Switch reads App reads from new column/path. Verify parity. vN+2
Contract Drop old column/code. Now safe — nothing depends on it. vN+3
Dangerous in one migrate
Rename column · change type incompatibly · add NOT NULL without default · long exclusive locks on huge tables. Prefer expand/contract + batched backfill.

Safe-ish online

  • Add nullable column
  • Create index CONCURRENTLY (Postgres)
  • Add new table

Needs expand/contract

  • Rename / split columns
  • Move data between tables
  • Change primary key shape
DashNote · Partial
Alembic online + Compose migrate service. Migrations are mostly create/alter — no expand→dual-write→contract discipline yet. Should be: adopt the pattern for any breaking column/table change; avoid long locks on hot tables.

11 Code examples TOGGLE

FastAPI matches DashNote. NestJS uses TypeORM/Prisma + AWS SDK parallels.

1. Presigned download URL

Blob metadata in DB · bytes in object store 
# FastAPI — mirrors DashNote storage + files router
@router.get("/files/{file_id}")
async def get_file(file_id: int, storage: StorageBackend, repo: FileRepo):
    file = await repo.get(file_id)
    url = storage.presigned_url(file.storage_key, expires_seconds=3600)
    if url is None:
        url = f"/files/{file.id}/download"  # local backend
    return {"id": file.id, "download_url": url, "mime": file.mime_type}

# S3-compatible backend
def presigned_url(self, key: str, expires_seconds: int = 3600) -> str:
    client = self._sync_session.client(**self._client_kwargs)
    return client.generate_presigned_url(
        "get_object",
        Params={"Bucket": self.bucket, "Key": key},
        ExpiresIn=expires_seconds,
    )
// NestJS — @aws-sdk/s3-request-presigner
@Get(":id")
async getFile(@Param("id") id: string) {
  const file = await this.files.findOne(id);
  const url = await getSignedUrl(
    this.s3,
    new GetObjectCommand({ Bucket: this.bucket, Key: file.storageKey }),
    { expiresIn: 3600 },
  );
  return { id: file.id, downloadUrl: url, mime: file.mimeType };
}

2. Connection pool + read/write engines

Pool knobs · optional read replica 
# FastAPI / SQLAlchemy — should-be upgrade over pool_pre_ping-only
write_engine = create_async_engine(
    settings.DATABASE_URL,
    pool_size=5,
    max_overflow=10,
    pool_recycle=1800,
    pool_pre_ping=True,

read_engine = create_async_engine(
    settings.DATABASE_READ_URL or settings.DATABASE_URL,
    pool_size=10,
    max_overflow=20,

async def get_write_db():
    async with AsyncSession(write_engine) as s:
        yield s

async def get_read_db():
    async with AsyncSession(read_engine) as s:
        yield s

3. Expand → dual-write → contract

Rename column without downtime 
# Alembic + app phases (conceptual)
# 1 Expand — migration
# op.add_column("notes", sa.Column("title_v2", sa.String(200), nullable=True))

# 2 Dual-write — app
async def update_title(note_id: int, title: str, db: AsyncSession):
    note = await db.get(Note, note_id)
    note.title = title      # old column (still required by old pods)
    note.title_v2 = title   # new column
    await db.commit()

# 3 Backfill — batched job
# UPDATE notes SET title_v2 = title WHERE title_v2 IS NULL LIMIT 1000;

# 4 Switch reads to title_v2, deploy, then contract:
# op.drop_column("notes", "title")
# op.alter_column("notes", "title_v2", new_column_name="title")
// NestJS — same phases with TypeORM migrations
// 1 Expand: ADD COLUMN title_v2 nullable
// 2 Dual-write in service:
async updateTitle(id: string, title: string) {
  await this.repo.update(id, { title, titleV2: title });
}
// 3 Backfill job in batches
// 4 Read titleV2 → drop title → rename

4. Tenant-safe list (avoids cross-tenant hotspot scans)

Composite index · always filter workspace 
# FastAPI — DashNote TenantRepository style
# Ideal index: (workspace_id, created_at DESC)

async def list_notes(db: AsyncSession, workspace_id: int, limit: int = 50):
    q = (
        select(Note)
        .where(Note.workspace_id == workspace_id)
        .order_by(Note.created_at.desc())
        .limit(limit)
    )
    return (await db.scalars(q)).all()

# Never: SELECT * FROM notes ORDER BY created_at  -- global hotspot
// NestJS
async listNotes(workspaceId: number, limit = 50) {
  return this.repo.find({
    where: { workspaceId },
    order: { createdAt: "DESC" },
    take: limit,
  });
}
// Index: @Index(["workspaceId", "createdAt"])

5. statement_timeout (kill runaway queries)

Budget every request 
# FastAPI — per-session budget (should-be)
async def get_db():
    async with AsyncSessionLocal() as session:
        await session.execute(text("SET LOCAL statement_timeout = '5s'"))
        yield session
// NestJS — on pool connect or per query
await this.ds.query("SET statement_timeout = '5s'");
// Prefer server default + override for heavy jobs
