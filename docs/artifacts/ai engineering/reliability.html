00 Fail-safe products

Reliability for LLM products is not “never wrong.” It is wrong answers don’t cause irreversible harm, outages don’t take down notes/files, and risky actions wait for a human.

Safe wrong

“I could not find that in your notes” beats a confident fake deadline.

Safe down

Qdrant/LLM out → core CRUD still up; AI returns 503 or empty retrieval.

Safe blocked

Destructive automation holds; agent mutations need ask / future approve.

Request → Guardrails → Model / tools → Gate? → User / system
Design rule
Prefer refuse / degrade / block over silent success with bad side effects. DashNote already encodes this in soft deps, citation grounding, and AutomationDecisionEngine fail-safe blocks.

01 Hallucination grounded RAG

The model states something that is not supported by retrieved notes (or invents citations, IDs, or tool outcomes). Confidence ≠ correctness.

Types that hurt products

  • Factual: wrong date / person / claim
  • Citation: fake chunk_id
  • Action: “note created” when tool failed
  • Extrinsic: world knowledge instead of notes

DashNote defenses today

  • RAG: answer only from context; refuse if empty
  • Citations mapped to retrieved set only
  • Fallback: top chunks if model cites nothing
  • Agent: search before inventing note IDs
# ai/prompts/rag.py — refuse is a feature
If context insufficient →
  "I could not find relevant information in your notes for this query."

# ai/services/rag_service.py — never trust LLM chunk IDs blindly
citations = [c for c in llm.cited_chunk_ids if c in retrieved_map]

02 Guardrails layered

Guardrails are checks around the model — input, process, and output — that constrain behavior. Soft (prompts) and hard (code) both matter; hard wins on risk.

Input → Model → Tools → Output
  • Input: auth, RBAC, rate limits, length caps
  • Process: allowlisted tools, step/timeout limits, structured schemas
  • Output: citation grounding, Pydantic validation, DLP (future)
  • RAG_SYSTEM_INSTRUCTION — ground + refuse + don’t leak prompt
  • WORKSPACE_ASSISTANT_PROMPT — mutate only if asked
  • Governance LLM: “when in doubt, block”

Soft rails reduce frequency; they do not bound blast radius alone.

  • JWT tenancy + build_rbac_filter
  • Tools → services only; no shell
  • AGENT_MAX_ITERATIONS / tool timeout
  • acompletion_structured + schema validation
  • should_execute_immediately confidence gate
RailSoft / hardDashNote
Grounded answers Soft + hard citations done
Mutation policy Soft prompt partial need HITL
Destructive automation Hard gate done
Output DLP / toxicity Hard filter todo
Input jailbreak filter Either todo
Ordering
Put hard rails closest to side effects (tools, DB writes, external send). Prompts are the outer soft layer — see also security.html.

03 Graceful degradation soft deps

When a dependency fails, the product sheds features instead of going fully down — and tells the user clearly (503 / empty AI / retry), not silent empty success.

HARD Postgres · Redis — GET /health must be 200
SOFT Qdrant · LLM providers — app boots; AI/indexing degrade
OPTIONAL Langfuse · LangSmith · remote Grafana — never block startup 
# main.py lifespan (concept)
ensure_notes_collection()  # try/except → log ERROR, continue
init_checkpointer()        # try/except → agent degrades; chat OK

# ai_routes/agent.py
RETRYABLE_EXCEPTIONS → 503 "LLM temporarily unavailable; retry shortly"
# Never silent empty 200 for agent failures

04 Human-in-the-loop UX gap

A human remains in the decision path for high-impact steps: review, edit, approve, or reject. HITL is the UX; approval gates are the mechanism.

When HITL pays off

  • Note create/update from agent
  • Deletes / merges / external notify
  • Bulk automation proposals
  • Low-confidence governance decisions

When to skip

  • Additive tags / file metadata
  • Idempotent vector upsert
  • Read-only RAG answers
  • High-confidence non-destructive
Agent wants create_note → interrupt → UI approve → resume checkpoint → tool runs
DashNote today
Soft HITL via prompt (“only if explicitly asked”). Hard HITL for automation is partially there: block + log [AUTOMATION_GOVERNANCE_BLOCK] — pending-action store / UI still future. Agent LangGraph interrupt UI not shipped (see agent.html).
Pre-action approve — pause before tool. Post-draft edit — show draft note, user saves. Queue review — automation pending list for owners. Escalation — agent → human when confidence low.
Postgres AsyncPostgresSaver already supports resume by thread_id. HITL interrupt needs that path + SSE approval_required event — don’t invent a second state store.

05 Approval gates automation

An approval gate is a programmatic stop that allows execution only when policy conditions are met (confidence, non-destructive, role, or human token).

—
Rule
Execute iff confidence ≥ 0.95 AND is_destructive = false 
# worker/automation/decision.py
SAFE_THRESHOLD = 0.95

should_execute_immediately(decision) →
  True  only if confidence >= 0.95 and not is_destructive
  False → log [AUTOMATION_GOVERNANCE_BLOCK], hold for review

# LLM / eval failure → _fail_safe_decision:
#   is_destructive=True, confidence=0.0  (always block)
GateTriggerStatus
AutomationDecisionEngine AI-initiated destructive jobs done
Skip gate for additive tasks tags / metadata / index done (by design)
Agent mutation interrupt create_note / update_note todo
Pending action inbox UI Blocked governance decisions todo
Role gate (owner approve) Workspace policy todo

06 More topics

Adjacent reliability practices for production AI.

Transient LLM errors → tenacity / ARQ retry. Fatal auth → don’t loop. Embeds and index upserts are idempotent (deterministic chunk IDs). Agent maps exhausted retries to 503, not empty 200.
Tool timeout and max iterations bound runaway agents. Future: circuit-break a flapping provider and fall back to chat-only mode.
Alert on governance blocks, agent 503 rate, RAG refuse rate spikes, and Qdrant errors. Soft dep health via optional GET /health/ai.
Agent 500 suggests “Try /ai/chat for direct RAG” — good pattern. Clients should show citations only after metadata event (streaming law).
Reliability regressions: hallucination goldens, refuse-on-empty, governance fail-safe unit tests (test_automation_decision.py). See evals.html · performance.html.

Don’t
Fail open on governance errors · return 200 with empty agent body · invent answers when retrieval is empty · skip HITL by widening tool power · block API boot on Langfuse/Qdrant · confuse soft prompt policy with a hard gate.

10 Checklist

  • Refuse / degrade / block preferred over silent bad success
  • Hallucination: ground + refuse + citation map
  • Guardrails: soft prompts + hard rails at side effects
  • Soft deps: Qdrant/LLM degrade; PG/Redis hard
  • HITL ≠ prompt-only; interrupt / queue for high impact
  • Approval gate: confidence ≥ 0.95 AND non-destructive; fail-safe block
  • Next: pending inbox → agent HITL → hallucination goldens
