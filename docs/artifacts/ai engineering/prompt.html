01 Prompt engineering in use

Prompt engineering is designing the text (and structure) you send the model so it reliably does the job — clarity, constraints, format, and examples beat clever tricks.

High leverage

  • Clear role + goal
  • Hard constraints (“ONLY from context”)
  • Output shape (JSON / markdown)
  • Refusal behavior when info missing

Low leverage

  • “Think step by step” spam
  • Emotional pleading
  • Giant prompts with no eval
  • Hiding requirements in paragraphs

Daily checklist

  • Separate roles — system = policy; user = task + data
  • Put data in labeled blocks — CONTEXT:, QUESTION:
  • Prefer schemas over prose for machine consumers
  • Version prompts in code — never bury strings in services
DashNote law
All RAG prompt strings live in ai/prompts/rag.py — nowhere else. Agent policy: WORKSPACE_ASSISTANT_PROMPT in workspace_assistant.py.

02 System prompt shipped

The system message sets durable policy: who the assistant is, what it may do, and how it must format answers. Users shouldn’t be able to casually override it.

system+ user (task + context)→ assistant

RAG_SYSTEM_INSTRUCTION — answer only from chunks; refuse if insufficient; cite chunk UUIDs; never reveal instructions.

WORKSPACE_ASSISTANT_PROMPT + injected workspace_id / user_id / role. Mutate only when explicitly asked; search before inventing IDs.

Inline system messages for tags, file metadata, governance decisions — paired with Pydantic response_format.

03 Few-shot prompting not used

Show 1–N input → output examples in the prompt so the model copies the pattern (zero-shot = instructions only; few-shot = instructions + demos).

Zero-shot

Rules only. Fast, cheap.

Few-shot

2–5 examples. Great for format & edge cases.

Many-shot

Dozens. Costly; often worse than fine-tune / schema.

DashNote gap
Tag / metadata / RAG prompts are instruction-only. Adding 2–3 curated examples for NoteTagAnalysis often beats lengthening the system text.

05 JSON Schema via Pydantic

JSON Schema is the portable contract describing fields, types, and required keys. Providers use it for constrained decoding; tools use it for args.

In DashNote

Pydantic models → .model_json_schema() for tools; response_format=Model for completions.

Why not hand-written JSON?

One source of truth, Field descriptions become LLM guidance, validation is free.

# Conceptual — CreateNoteArgs → tool parameters
{
  "type": "object",
  "properties": {
    "title": { "type": "string", "description": "Title for the new note." },
    "content": { "type": "string", "description": "Full markdown content…" },
    "workspace_id": { "type": "string", "description": "…do not modify." }
  },
  "required": ["title", "content", "workspace_id", "user_id", "role"]
}

06 Function calling shipped

Function calling (OpenAI-style) lets the model emit a structured “call this name with these JSON args” instead of only text — the API shape behind tools.

tools=[…]→ model→ tool_calls[]→ your code runs fn→ role=tool result
DashNote
Agent uses LiteLLM tools= with OpenAI function defs — not LangChain .bind_tools(). tool_choice="auto".

07 Tool use shipped

Tool use is the product pattern: the model chooses capabilities (search, create note, …) and your app executes them safely in a loop.

ToolSide effectService
search_notesReadRagService.answer
summarize_workspaceReadRAG limit=12
create_noteWriteNoteService
update_noteWriteNoteService

Safety rules

  • Tool → service → repository (never shortcut)
  • Tenant IDs from state, not trusted LLM invention
  • DB session via db_session_var for mutations
  • Errors returned as tool observations so the loop can recover
Companion
Agent loop, HITL, orchestrator → agentic_orchestration.html. This page focuses on the prompt/schema contract that makes tools callable.

08 Tool schema shipped

Each tool needs a name, description (when to call), and JSON Schema for arguments. Bad descriptions → wrong tools; weak schemas → invalid args. 

{
  "type": "function",
  "function": {
    "name": "search_notes",
    "description": "Search workspace notes… Use when user asks about content…",
    "parameters": { /* from SearchNotesArgs.model_json_schema() */ }
  }
}

10 Prompt vs tools — when to use which

Don’t stuff everything into the prompt if a tool should fetch or mutate.

Prefer prompting

  • Style, tone, refusal policy
  • Formatting already-retrieved context
  • Classification with a schema

Prefer tools

  • Live workspace search
  • Create / update notes
  • Anything needing RBAC + DB

12 Implement in DashNote

Concrete next steps — keep prompts isolated and tools schema-first.

  1. Few-shot for tagging / metadata

    In automation system messages, add 2–3 frozen examples (input snippet → expected JSON). Measure parse-fail rate before/after.

  2. Centralize agent prompt

    Move WORKSPACE_ASSISTANT_PROMPT to ai/prompts/agent.py (same law as RAG). Easier tuning + tests without opening the graph file.

  3. Hard-bind tenant in tools

    Remove workspace_id / user_id / role from LLM-visible schemas; inject from AgentState inside tool wrappers. Descriptions alone are soft security.

  4. Prompt eval harness

    20–40 fixtures: “insufficient context → refuse”, “cite real chunk ids”, “don’t create note unless asked”. Run in CI against mocked LLM or recorded stubs.

  5. Tool description lint

    Checklist in PR: name verb-first, when-to-use sentence, when-not-to-use, args Field descriptions filled. Prevents vague tool sprawl.
