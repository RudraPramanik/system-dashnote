Data modeling & SQL

How to shape relational data, make queries fast and correct, and use transactions without surprises — with PostgreSQL as the primary engine. DashNote callouts map what this repo already does.

Full curriculum Postgres-first SQLAlchemy · TypeORM

00 Overview

The database is the source of truth for most backends. Schema + indexes + transaction boundaries decide correctness under concurrency — more than clever application code.

What this book covers
  1. Model entities, keys, and relationships
  2. Normalize for integrity; denormalize for read paths — with eyes open
  3. Index for the queries you run; read EXPLAIN
  4. Kill N+1; understand ORM load strategies
  5. ACID, isolation levels, and when you need stronger guarantees (Postgres)
DashNote stack
Postgres 16 · SQLAlchemy 2 async + asyncpg · Alembic · Redis cache-aside for some lists. Vectors live in Qdrant (not SQL) — relational core stays in Postgres.

01 Entities, keys & relationships

Start from the domain, not from tables that mirror API JSON.

Keys

  • Primary key — stable identity (bigint, UUID). Prefer opaque IDs for public APIs.
  • Natural key — business uniqueness (email, storage_key) enforced with UNIQUE.
  • Foreign key — relationship integrity; decide ON DELETE (CASCADE / RESTRICT / SET NULL).
  • Composite key — membership (user_id, workspace_id) style when the pair is the identity.

Relationship shapes

CardinalitySQL patternExample
1:1FK unique on one sideUser ↔ profile
1:NFK on the many sideThread → messages
N:MJoin tableNotes ↔ files (attachments)

Multi-tenant modeling

Shared schema + tenant column

workspace_id on every row. Simplest ops; every query must filter.

Schema / DB per tenant

Strong isolation; expensive ops. Rare until enterprise compliance demands it.

Invariant
Tenant isolation is a data rule. App filters help; FKs + unique constraints + (optionally) Postgres RLS make leaks harder.
DashNote · Partial
WorkspaceTenantMixin.workspace_id on notes/files/notebooks/pages/threads — indexed, but often without FK to workspaces. Membership uses real FKs. Repos apply tenant_filter(). Soft-delete mixin exists but threads use is_active instead.

02 Normalization

Normalization reduces update anomalies by storing each fact once.

FormRule (practical)Smell if violated
1NF Atomic cells; no repeating groups as columns tag1, tag2, tag3 columns
2NF Non-key attrs depend on whole composite key Order-line stores customer address
3NF No transitive deps (A→B→C stored on A) Note stores author_email that duplicates users
BCNF Every determinant is a candidate key Overlapping unique rules causing redundancy

Why normalize first

  • Single place to update a fact → fewer bugs
  • Constraints become enforceable
  • Storage and write amplification drop
Guideline
Design to ~3NF for the write model. Denormalize deliberately for hot read paths — never by accident because the API JSON looked nested.

03 Denormalization tradeoffs

Copying data speeds reads and costs consistency. Price it explicitly.

Good reasons

  • Read path is 100× hotter than writes
  • Joins cross service boundaries you can’t afford
  • Derived fields (summary, counts) that are expensive
  • Event/snapshot models for history

Costs

  • Dual writes / sync lag / drift
  • Larger rows → worse cache hit rate
  • Harder migrations when shape changes
  • Bugs that only show under races

Common patterns

  • Cached counters — message_count on thread; update in same transaction as insert
  • Materialized columns — search document text, AI summary
  • JSONB blobs — flexible attrs / tags when you don’t join on them often
  • Read models — CQRS projection tables fed by events
DashNote · Covered (intentional denorm)
Files store extracted_text, summary, tags (JSONB) written by workers — classic read-optimized denorm. Notes tags JSONB similarly. Keep the source of truth for membership/auth fully normalized.

04 Constraints = correctness tools

If the database can enforce it, don’t leave it to hopeful application code alone.

  • NOT NULL — required fields
  • UNIQUE — natural keys, idempotent insert targets
  • FOREIGN KEY — no orphan rows
  • CHECK — enums/ranges (role IN (...))
  • EXCLUDE (Postgres) — no overlapping ranges
Race example
SELECT max(version)+1 without a UNIQUE(page_id, version) will double-allocate under concurrency. Prefer unique constraints + retry, or INSERT ... ON CONFLICT.
DashNote
Unique email / storage_key; CHECK on AI message roles; FKs with CASCADE on membership/pages/messages. Should be: FK workspace_id → workspaces where missing; unique page versions.

05 Indexes

Indexes trade write cost + disk for faster lookups and sorts. Index the queries, not every column.

B-tree (Postgres default)

  • Equality and range: =, <, >, BETWEEN, ORDER BY
  • Left-most prefix of composites: (workspace_id, created_at) helps WHERE workspace_id=?
  • Does not help leading-wildcard LIKE '%foo'

Covering / index-only scans

If the index contains all columns the query needs, Postgres can avoid heap fetches (index-only scan when visibility map allows). In Postgres create covering indexes with INCLUDE (col) (non-key columns stored in the index leaf). 

CREATE INDEX ix_notes_ws_created
  ON notes (workspace_id, created_at DESC)
  INCLUDE (title, is_private);

Other Postgres index types (when needed)

TypeUse
GINJSONB containment, arrays, full-text
GiSTRanges, geometry, some fuzzy search
BRINHuge append-only time-series tables
HashEquality only — rarely preferred over B-tree
PartialWHERE deleted_at IS NULL — smaller, hotter indexes
ExpressionLOWER(email) for case-insensitive unique

Composite index design

  • Equality columns first, then range/sort columns
  • Match tenant filters: nearly always lead with workspace_id
  • Don’t duplicate indexes that are prefixes of each other without reason
DashNote · Partial
Indexes on workspace_id, created_by, composites on files/messages. Should be: notes visibility composites; GIN on tags if you filter by tag; review unused indexes with pg_stat_user_indexes.

06 Query plans

Guessing is slow. EXPLAIN (ANALYZE, BUFFERS) tells you what Postgres actually did.

How to read a plan (essentials)

  • Seq Scan — full table read; OK for tiny tables, bad for hot large filters
  • Index Scan / Index Only Scan — using an index
  • Bitmap Heap Scan — combine indexes then fetch rows
  • Nested Loop / Hash Join / Merge Join — join strategies
  • rows vs actual rows — bad estimates → wrong plan (needs ANALYZE / better stats)
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT id, title FROM notes
WHERE workspace_id = 7 AND is_private = false
ORDER BY created_at DESC
LIMIT 20;

Tuning loop

  1. Identify slow query (logs, pg_stat_statements)
  2. EXPLAIN ANALYZE on realistic data volume
  3. Add/adjust index or rewrite query (avoid SELECT *, functions on indexed cols)
  4. Re-measure; watch write overhead of new indexes
DashNote · Gap
No EXPLAIN discipline or pg_stat_statements in-repo. Should be: habit before “optimize” PRs; enable stats in staging.

07 The N+1 problem

1 query for parents + N queries for children = latency cliff as N grows.

Classic form

-- 1 query
SELECT * FROM notes WHERE workspace_id = 7;
-- then for EACH note (N queries):
SELECT * FROM note_attachments WHERE note_id = ?;

Fixes

  • JOIN or two-step: load parents, then WHERE parent_id IN (...)
  • ORM: selectinload / joinedload (SQLAlchemy), relations / leftJoinAndSelect (TypeORM)
  • Don’t lazy-load in list endpoints — return DTOs without nested graphs, or eager deliberately
  • Batch DataLoader pattern for GraphQL

selectinload

2 queries total (parents + all children IN ids). Usually best for collections.

joinedload

1 big JOIN; can multiply rows — careful with pagination.

DashNote · Partial
Auth uses selectinload; Note↔File M2M is lazy="selectin"; AIThread messages noload. Risk: listing notes may pull attachments for every row. Notes list also unbounded (no pagination).

08 ACID — when you need it

MeaningIf you skip it
Atomicity All-or-nothing multi-statement change Half-created user+workspace
Consistency Constraints hold after commit Orphans, negative balances
Isolation Concurrent txns don’t see illegal intermediate states Lost updates, double spend
Durability Committed data survives crash (WAL) Silent data loss after ACK
When you need a transaction
Anytime two+ writes must succeed together, or read-modify-write must not race (inventory, balances, “create A then B”, version counters). Single-row insert by PK often doesn’t need ceremony — but multi-entity registration does.

09 Transactions in practice

  • Keep transactions short — no HTTP calls / LLM / sleep inside a txn
  • One logical unit of work per commit
  • On error: rollback; don’t reuse a doomed session
  • Prefer DB constraints + retry over long locks
  • Outbox pattern: write business row + outbox row in same txn, publish async
DashNote · Partial
Repos commit per operation; register_user flush+single commit is a good multi-entity example. No explicit isolation settings; no request-scoped unit-of-work wrapper. Engine: pool_pre_ping=True only — should set pool_size / overflow for prod.

10 Isolation levels (PostgreSQL)

Postgres default is READ COMMITTED. Stronger levels cost concurrency; pick them when anomalies hurt money or uniqueness.

Level Dirty read Non-repeatable Phantom Postgres notes
Read Uncommitted ——— Treated like Read Committed in Postgres
Read Committed (default) NoYesYes Each statement sees latest committed data
Repeatable Read NoNoNo* Snapshot; serialization failures possible (*Postgres prevents phantoms here)
Serializable NoNoNo SSI; may abort with 40001 — retry

Anomalies you should recognize

  • Lost update — two txns read same row, both write; last write wins
  • Write skew — each txn checks a constraint on different rows; together they break it (needs Serializable or explicit locks)
  • Non-repeatable read — same SELECT twice, different values mid-txn

What to use when (Postgres)

Read Committed is enough

  • Typical CRUD
  • Idempotent upserts with UNIQUE
  • Most DashNote-style note/file writes

Raise the bar

  • Balances / inventory → row locks or Serializable + retry
  • Unique business invariants across rows → Serializable or careful locking
  • Report “as of one snapshot” → Repeatable Read
-- Session / transaction scoped
BEGIN ISOLATION LEVEL REPEATABLE READ;
-- or
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
MySQL vs Postgres
MySQL InnoDB Repeatable Read ≠ Postgres RR semantics. Don’t copy isolation advice across engines blindly. This guidebook assumes PostgreSQL.

11 Locking

  • SELECT ... FOR UPDATE — lock rows you’ll update (skip locked / nowait variants)
  • Optimistic — version column / xmin; update WHERE version=?; retry on 0 rows
  • Pessimistic — hold locks; simpler logic, worse contention
  • Advisory locks — app-level lock keys in Postgres for job exclusivity
  • Unique constraints beat soft “check then insert” every time
DashNote · Gap
Page versioning via max+1 without unique/lock is a classic race. Should be: UNIQUE(page_id, version) + retry, or FOR UPDATE on parent page.

12 PostgreSQL toolkit

Features you’ll actually use in product backends — beyond generic SQL.

Types & storage

  • JSONB — flexible docs + GIN
  • UUID / gen_random_uuid()
  • Arrays (use sparingly vs child tables)
  • TIMESTAMPTZ always for real time

Write patterns

  • INSERT ... ON CONFLICT upsert
  • RETURNING to avoid extra SELECT
  • CTEs for multi-step writes
  • LISTEN/NOTIFY (light fan-out)

Safety & scale

  • Partial indexes
  • Row Level Security (RLS) for tenant defense-in-depth
  • Logical replication / partitioning (later scale)
  • pg_stat_statements for hot queries

Search

  • tsvector / GIN for full-text
  • Or external OpenSearch when relevance gets serious
-- Upsert (Postgres)
INSERT INTO files (id, workspace_id, storage_key, name)
VALUES ($1, $2, $3, $4)
ON CONFLICT (storage_key) DO NOTHING
RETURNING id;

-- JSONB containment (needs GIN)
SELECT * FROM notes
WHERE workspace_id = $1 AND tags @> '["ai"]'::jsonb;
DashNote · Partial
Uses JSONB tags/citations, UUID PKs on files, gen_random_uuid, on_conflict_do_nothing upserts. No RLS, no GIN on tags, no full-text in Postgres (search leans on Qdrant for AI).

13 Migrations

  • Expand → migrate → contract for zero-downtime
  • Never rename/remove columns in one step while old code runs
  • Create indexes CONCURRENTLY on large Postgres tables (outside a txn in Alembic carefully)
  • Backfills in batches; lock timeouts
  • Migrations are code — review for locks (ALTER TYPE, rewrite tables)
DashNote · Covered
Alembic revisions for auth, notes, files, tags JSONB, AI threads, etc. Sync URL for migrations; async engine for app.

14 ORM pitfalls

  • Lazy load after session closed → errors or hidden queries
  • expire_on_commit surprises — know your session settings
  • Loading graphs you don’t need (over-fetch)
  • Generating N queries in loops
  • Bypassing constraints by “fixing later”
  • Huge IN lists — chunk them
Guideline
ORM for CRUD productivity; raw SQL / text() when the plan matters. Always know the SQL your ORM emits in hot paths.

17 Code examples TOGGLE

SQLAlchemy async (DashNote-like) ↔ NestJS TypeORM. SQL snippets are engine-truth.

1. Tenant-scoped model + composite index

Schema 
# SQLAlchemy 2 — Postgres JSONB + composite index
import sqlalchemy as sa
from sqlalchemy.dialects.postgresql import JSONB
from sqlalchemy.orm import Mapped, mapped_column

class Note(Base):
    __tablename__ = "notes"
    __table_args__ = (
        sa.Index("ix_notes_ws_created", "workspace_id", sa.text("created_at DESC")),
        sa.ForeignKeyConstraint(["workspace_id"], ["workspaces.id"]),
    )

    id: Mapped[int] = mapped_column(primary_key=True)
    workspace_id: Mapped[int] = mapped_column(nullable=False, index=True)
    title: Mapped[str] = mapped_column(sa.String(255))
    tags: Mapped[list] = mapped_column(JSONB, server_default=sa.text("'[]'::jsonb"))
// TypeORM + Postgres
import { Entity, PrimaryGeneratedColumn, Column, Index, ManyToOne } from 'typeorm';

@Entity('notes')
@Index('ix_notes_ws_created', ['workspaceId', 'createdAt'])
export class Note {
  @PrimaryGeneratedColumn() id: number;

  @Index()
  @Column() workspaceId: number;

  @Column({ length: 255 }) title: string;

  @Column({ type: 'jsonb', default: () => "'[]'" })
  tags: string[];

  @ManyToOne(() => Workspace, (w) => w.notes)
  workspace: Workspace;
}

2. Avoid N+1 on lists

Eager / select-in 
# SQLAlchemy — 2 queries, not N+1
from sqlalchemy import select
from sqlalchemy.orm import selectinload

stmt = (
    select(Note)
    .where(Note.workspace_id == workspace_id)
    .options(selectinload(Note.attachments))  # one IN (...) query
    .order_by(Note.created_at.desc())
    .limit(20)
)
notes = (await session.execute(stmt)).scalars().all()

# Better for API lists: don't load attachments at all — map to NoteRead DTO
// TypeORM — join or QueryBuilder relation load
const notes = await this.noteRepo.find({
  where: { workspaceId },
  relations: { attachments: true }, // watch over-fetch
  order: { createdAt: 'DESC' },
  take: 20,
});

// Or explicit:
await this.noteRepo
  .createQueryBuilder('n')
  .leftJoinAndSelect('n.attachments', 'a')
  .where('n.workspace_id = :wid', { wid: workspaceId })
  .orderBy('n.created_at', 'DESC')
  .take(20)
  .getMany();

3. Transaction + isolation

Multi-write unit of work 
# SQLAlchemy async — register-style multi-entity commit
async with session.begin():  # commits/rollbacks as a block
    user = User(email=email, ...)
    session.add(user)
    await session.flush()  # get user.id

    workspace = Workspace(name=name, ...)
    session.add(workspace)
    await session.flush()

    session.add(WorkspaceUser(user_id=user.id, tenant_id=workspace.id, role="owner"))
    # exit begin() → COMMIT

# Stronger isolation when needed:
await session.connection(execution_options={
    "isolation_level": "REPEATABLE READ"  # or SERIALIZABLE
})
// TypeORM — QueryRunner transaction
await this.dataSource.transaction(
  'SERIALIZABLE', // or 'READ COMMITTED' (default)
  async (manager) => {
    const user = await manager.save(User, { email, ... });
    const workspace = await manager.save(Workspace, { name, ... });
    await manager.save(WorkspaceUser, {
      userId: user.id,
      tenantId: workspace.id,
      role: 'owner',
    });
  },
);

4. Optimistic locking / lost update

Version column 
# Optimistic concurrency
stmt = (
    update(Note)
    .where(Note.id == note_id, Note.version == expected_version)
    .values(title=new_title, version=expected_version + 1)
)
result = await session.execute(stmt)
if result.rowcount == 0:
    raise ConflictError("note was modified by someone else")
await session.commit()
// TypeORM @VersionColumn
@Entity()
export class Note {
  @VersionColumn() version: number;
  // TypeORM increments & fails update on stale version
}

try {
  note.title = newTitle;
  await this.noteRepo.save(note);
} catch (e) {

5. Postgres upsert + EXPLAIN habit

-- Correctness: unique natural key + upsert
INSERT INTO files (id, workspace_id, storage_key, name, mime_type, size_bytes)
VALUES ($1,$2,$3,$4,$5,$6)
ON CONFLICT (storage_key) DO UPDATE
SET name = EXCLUDED.name
RETURNING *;

-- Performance: always measure
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM files
WHERE workspace_id = $1 AND created_by = $2
ORDER BY created_at DESC
LIMIT 20;

18 Mastery checklist

Modeling

  • Choose PKs / natural keys / FK delete rules deliberately
  • Normalize a schema to ~3NF, then list intentional denorms
  • Use UNIQUE/CHECK/FK as correctness tools
  • Model multi-tenant rows safely (filter + constraint story)

Queries

  • Design a composite B-tree for a tenant list+sort query
  • Explain covering indexes / INCLUDE
  • Read an EXPLAIN ANALYZE and spot Seq Scan vs Index Scan
  • Fix an N+1 (SQL + ORM strategy)
  • Know when to use GIN on JSONB

Transactions (Postgres)

  • State ACID in one sentence each
  • Know Postgres default isolation and what anomalies remain
  • Pick RR vs Serializable vs row locks for a race
  • Keep transactions short; retry on serialization failure
  • Prefer UNIQUE + upsert over check-then-insert

DashNote gaps you can name

  • workspace_id FK gaps
  • Notes list pagination / over-fetch
  • Page version race
  • Pool sizing + EXPLAIN habit
