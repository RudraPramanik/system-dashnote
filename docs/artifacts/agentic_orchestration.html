Agentic orchestration

The backbone of modern AI apps: agents that reason, call tools, loop until done, and run inside workflows — mapped onto DashNote’s LangGraph workspace assistant and what to build next.

Agent loop ✓ 4 tools ✓ LangGraph ✓ Skills ✗ HITL ✗ Orchestrator ✗

01 What is an agent shipped

An agent is an LLM that can take actions (tools) in a loop until it decides the goal is met — not just a one-shot completion.

Chat / RAG

  • Retrieve → generate once
  • No side effects
  • Fast, predictable

Agent

  • Model chooses tools
  • May mutate state (create note)
  • Multi-step, variable latency
Minimal definition
Agent = policy (LLM + prompt) + actions (tools) + loop (observe → act → observe) + stop condition (final answer or max steps).
DashNote
POST /ai/agent · graph in ai/workflows/workspace_assistant.py. Coexists with fast RAG at /ai/chat* — never replace chat with agent.

02 Agent loop shipped

The loop is the runtime: call model → if tool calls, execute → feed results back → call model again → until end or limit.

START→ agent→ tools?→ tools→ agent→ END
RouteWhenDashNote
toolsModel emitted tool_callsshould_continue
endFinal text answerNo tool_calls
limitToo many stepsAGENT_MAX_ITERATIONS=10
Safety
Every call_model increments steps_taken. Without a max-iteration guard, a confused model can burn tokens forever.

03 Tool use shipped

Tools are the agent’s hands. The model picks a name + JSON args; your code executes and returns a string observation.

Design laws

  • Schema — Pydantic args_schema; reject free-form junk
  • Descriptions — tell the model when to call, not just what
  • Service boundary — tool → service → repository (never shortcut)
  • No tenant args from LLM trust — inject workspace_id from state
  • Errors as observations — return “failed: …” so the loop can recover
ToolServiceSide effect
search_notesRagService.answerRead
summarize_workspaceRAG limit=12Read
create_noteNoteServiceWrite
update_noteNoteServiceWrite

StructuredTool + schemas in ai/tools/schemas.py · registry get_note_tools().

Graph uses LangGraph ToolNode; model call uses OpenAI function defs — not LangChain .bind_tools().

Mutation tools need AsyncSession but the LLM cannot invent a DB handle.

Solution: db_session_var (ContextVar) set by the tool node before invoke.

04 Agent skills not yet

Skills are packaged capabilities beyond a raw function — playbooks the agent can load: instructions, checklists, optional tools, and when to use them.

Tool

Atomic action: search, create.

Skill

Procedure: “weekly review” = search → summarize → draft note.

Persona

Style + constraints in the system prompt.

Why skills matter

  • Keep the base prompt small; load skills on demand
  • Encode domain SOPs without hard-coding a DAG for every case
  • Enable progressive disclosure (Cursor-style skill files)
# skills/weekly_review.md
name: weekly_review
when: user asks for weekly summary / standup prep
steps:
  1. summarize_workspace
  2. search_notes for open risks
  3. create_note only if user asks to save
tools: [summarize_workspace, search_notes, create_note]

Today: one fixed system prompt + 4 always-on tools.

Next: skill registry → inject matching skill text into the system message; optionally filter the tool list per skill.

05 Workflows partial

A workflow is a graph of steps with typed state. Agents are one node type inside workflows — not the only kind.

StyleControlUse when
Sequential DAGCode-fixed edgesETL, known pipelines
Agent loopModel chooses next toolOpen-ended tasks
HybridDAG with agent nodesMost production systems

Slice 6: StateGraph · AgentState · nodes agent + tools.

Checkpointer: AsyncPostgresSaver (psycopg3) — execution memory, separate from product AIThread.

Config: {"configurable": {"thread_id": thread_id}}.

Slice 7 event bus is also a workflow — but deterministic:

file.uploaded → extract → fan-out index + metadata. No LLM choosing edges.

Don’t confuse worker DAGs with the agent loop; they solve different problems.

Rule
Prefer a fixed workflow when steps are known. Prefer an agent when the path depends on intermediate observations. Prefer hybrid when both apply.

06 Orchestrator not yet

An orchestrator decides which agent / workflow / skill runs for a request — routing, parallel fan-out, and aggregation.

Without orchestrator

Client picks /ai/chat or /ai/agent. One graph, four tools.

With orchestrator

Ingress router: FAQ → chat; “create note” → agent; research → sub-agent; report → DAG.

Common topologies

  • Router — classify intent → one specialist
  • Supervisor — central LLM delegates to workers, merges answers
  • Handoff — agent A transfers control + summary to agent B
  • Fan-out / fan-in — parallel specialists → synthesizer
Companion
Multi-agent, handoff, harness, autonomy levels → see agent.html. This page focuses on the single-agent loop + when you need an orchestrator at all.

07 Patterns: ReAct · Plan · Router

Named recipes you’ll see in papers and frameworks — all map onto graphs.

Reason + Act interleaved: think → tool → observe → think…

DashNote’s loop is ReAct-shaped (tool_choice auto, no separate planner node).

First produce a plan (steps), then execute each step (often with tools), then revise.

Better for long tasks; more latency. Not in DashNote yet — add a planner node before agent.

Cheap classifier (or small LLM) picks chat vs agent vs skill before the heavy loop.

Best ROI next step for cost control — see Cost Optimization guide.

09 Guards & HITL partial

Autonomy without brakes is a liability — especially with write tools.

Have today

  • AGENT_MAX_ITERATIONS
  • AGENT_TOOL_TIMEOUT
  • Prompt: mutate only if explicitly asked
  • Service-layer RBAC on notes
  • LLM retry → HTTP 503
  • AutomationDecisionEngine (worker destructive acts)

Missing

  • LangGraph interrupt before create/update
  • Allowlist of tools per role
  • Budget caps (tokens / $ per turn)
  • Confirmation UI for mutations
HITL pattern
Before write tools: interrupt() → return pending action to client → user approves → Command(resume=…). Highest leverage for agent trust.

12 Implement in DashNote

Ordered upgrades that respect Slice 6 laws. Don’t jump to multi-agent first.

  1. HITL interrupt on write tools

    Wrap create_note / update_note with LangGraph interrupt. Stream a pending_action SSE event; resume on user confirm. Highest trust win for demos and production.

  2. Intent router before the loop

    Lightweight classifier (rules or small LLM): Q&A → RagService; mutations / multi-step → agent graph. Cuts cost and latency for 80% of traffic.

  3. Skill registry

    Add ai/skills/*.md (or YAML). Match on user message; inject into system prompt; optionally subset tools. Keep base WORKSPACE_ASSISTANT_PROMPT short.

  4. File-aware tools

    search_files over files_chunks with same RBAC pattern. Still tool → service; extend retrieval wrapper — don’t raw-query Qdrant from tools.

  5. Orchestrator / specialists (later)

    Only when tool count or prompt overcrowds. Supervisor + research/writer workers. Details in agent.html. Blueprint goal.md treats multi-agent as late stage.

  6. Agent eval harness

    Scripted tasks: “create note X”, “update Y after search”. Assert tool sequence + side effects. Extend scripts/e2e_agent_test.py + pytest fixtures.

Minimal router sketch

# ai_routes or thin service — conceptual
intent = classify(message)  # "rag" | "agent" | "reject"
if intent == "rag":
    return await RagService.answer(...)
if intent == "agent":
    return await run_workspace_assistant(...)
Laws to keep
Chat routes untouched · tools call services only · tenant from state not LLM · checkpointer ≠ product threads · append-only settings · no infinite loops without AGENT_MAX_ITERATIONS.
