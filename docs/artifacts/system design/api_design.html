API design

A practical guideline for designing production HTTP APIs — resources, contracts, evolution, and failure modes. DashNote callouts show what this repo already does and what a production system should still add.

Full curriculum DashNote-mapped FastAPI · NestJS

00 Overview

An API is a long-lived product surface. Good design optimizes for client clarity, safe change, and predictable failure — not for matching your internal table layout.

What this book covers
  1. Model resources and URLs that stay stable
  2. Choose methods, bodies, and status codes deliberately
  3. Ship list/query, error, and idempotency contracts
  4. Decide sync vs async vs webhooks vs streams
  5. Version, deprecate, and document without breaking clients
Client intent→ Resource + method→ AuthZ · validate→ Sync work or enqueue→ Stable response shape
DashNote shape
JWT-scoped flat REST (/notes, /files, /auth, /ai/*) plus SSE for chat/agent. Workspace comes from JWT wid, not the path. OpenAPI live only when DEBUG.

01 Design principles

Rules that keep APIs usable under growth and team churn.

1. Client-first contracts

Name what the product does, not your ORM. Hide join tables and storage quirks.

2. Predictable semantics

Same verb + status meaning everywhere. Don’t invent “200 with error in body” for writes.

3. Explicit failure

Errors are part of the API. Typed codes + stable fields beat free-form strings alone.

4. Safe evolution

Additive changes preferred. Breaking changes need versioning or dual-run periods.

5. Least surprise

GET never mutates. POST creates/actions. PATCH partial. DELETE removes (or soft-deletes consistently).

6. Bound the expensive

Pagination defaults, rate limits, payload size limits, and timeouts are design — not ops afterthoughts.

Guideline
If two endpoints do the same kind of thing differently (list shape, error shape, auth), clients will forever special-case you. Standardize early.

02 Resources & URL design

URLs identify resources. Verbs are HTTP methods — not verbs jammed into paths.

Resource modeling

  • Nouns in plural: /notes, /files, /workspaces
  • IDs opaque to clients: /notes/{id} — prefer stable public IDs (UUID) over leaking sequence if enumeration is a risk
  • Collections vs items: list on collection, detail on item
  • Actions that aren’t CRUD: POST /files/{id}/attach/{note_id} or POST /notes/{id}:publish (pick one style and stick to it)

Flat vs nested

StyleExampleWhen
Flat /notes/{id} Resource has its own identity; parent is context (auth/tenant)
Nested /ai/threads/{id}/messages Child only makes sense under parent; lifecycle tied together
Cross-link action POST /files/{id}/attach/{note_id} Relating two peers without inventing a third resource yet

Tenancy in the URL

Path tenancy

/workspaces/{wid}/notes — explicit, good for multi-workspace UIs and admin tools.

Token tenancy

Workspace from JWT — shorter URLs; harder to “act as” another tenant without impersonation APIs.

DashNote · Covered
Flat resources + JWT wid / role. Nested where it fits: /workspaces/members, /ai/threads/{id}/messages, /files/{id}/download. Notes are not nested under notebooks in the path today.

Naming rules that age well

  • kebab-case or snake for rare multi-word path segments — be consistent
  • Don’t encode filters in path (/notes/active) — use query params
  • Avoid deep nesting (>2 levels) — clients and caches hate it
  • Prefer one canonical URL per resource (no duplicate list endpoints without reason)

03 HTTP methods — safe, unsafe, idempotent

Method choice is a correctness contract, not a style preference.

MethodSafe?Idempotent?Use for
GET Yes Yes Read / list / download. Never mutate.
HEAD Yes Yes Metadata only (existence, size, ETag)
POST No No* Create, actions, non-idempotent commands (*make idempotent with keys)
PUT No Yes Full replace of a resource at a known URI
PATCH No Usually Partial update — document merge semantics
DELETE No Yes Remove; second call should be 404 or 204 consistently
Common mistake
GET /notes/delete?id=1 or POST /getNotes — breaks caches, CDNs, and every HTTP assumption.
DashNote · Covered
GET reads · POST create/actions · PATCH partial · DELETE remove · no PUT. Examples: POST /notes/, PATCH /notes/{id}, POST /files/upload, POST /ai/chat, DELETE /notes/{id} → 204.

04 Request & response bodies

Schemas are the API. Handlers should be thin adapters over validated DTOs.

Guidelines

  • Separate write/read models — Create / Update / Read (DashNote does this for notes)
  • Optional vs required — PATCH fields optional; CREATE required fields explicit
  • Don’t overshare — strip secrets, internal flags, other tenants’ fields
  • Stable field names — rename is a breaking change
  • Types over strings — booleans, enums, ISO-8601 timestamps
  • Envelope policy — either raw resource or { data, meta } — pick one for lists and stick to it

Content types

  • application/json — default for APIs
  • multipart/form-data — uploads (POST /files/upload)
  • text/event-stream — SSE streams
  • Prefer explicit Content-Type; reject ambiguous bodies in strict APIs

Partial updates

PATCH should mean “merge these fields.” Document null semantics: is null “clear field” or “ignore”? JSON Merge Patch vs JSON Patch — choose one.

DashNote · Covered
Pydantic DTOs per module (notes/schemas.py, files/schemas.py, auth, AI). response_model= on most routes. Notes: NoteCreate / NoteUpdate / NoteRead.

05 Versioning

Version when you must break; prefer additive change first.

StrategyExampleProsCons
URL path /v1/notes Obvious, cache-friendly, easy to route Duplicates surface area
Header Accept: application/vnd.dashnote.v2+json Clean URLs Harder to debug; proxy/cache care
Query ?api_version=2 Easy to try Easy to forget; weak for public APIs
No version + evolve Additive fields only Simple early product Cornered when you need a hard break
Guideline
Ship /v1 (or equivalent) before external clients lock in. Internal-only apps can delay — but document the compatibility promise.
DashNote · Gap
Routes are unversioned (/notes, /ai/chat). App metadata version="1.0.0" is not an API version. Should be: introduce /v1 (or header policy) before public/mobile clients proliferate.

06 Pagination, filtering, sorting

Unbounded lists are a latency and memory bug waiting to happen.

Pagination styles

Offset

skip/limit or page/page_size. Simple; drifts under concurrent writes.

Cursor

cursor + limit. Stable for feeds/timelines; harder for “jump to page 50”.

Keyset

Order by indexed column + after_id. Best at scale for append-heavy data.

List response contract (recommended)

{
  "items": [ /* resources */ ],
  "total": 1234,          // optional for cursor pages
  "skip": 0,
  "limit": 20,
  "next_cursor": null     // if using cursors
}

Filtering & sorting

  • Query params: ?is_private=true&created_after=2026-01-01
  • Sort: ?sort=-created_at or ?sort_by=created_at&order=desc
  • Allowlist sortable/filterable fields — never pass raw SQL fragments
  • Cap limit (e.g. max 100); document defaults
  • Sparse fieldsets (?fields=id,title) — optional optimization for mobile
DashNote · Partial
Covered: GET /files/?skip=&limit= returns FileListResponse with total. Gap: GET /notes/, notebooks, threads, members return full lists without pagination/filter/sort query contracts. Should be: same list envelope everywhere; cursor for activity/feed-like AI threads later.

07 Error shapes

Clients automate against errors. Strings alone don’t scale.

What a good error includes

  • HTTP status that matches the class of failure
  • Stable machine code (e.g. note_not_found, rate_limited)
  • Human message (safe to show; no secrets)
  • Optional details / field errors for validation
  • Optional request_id for support

Recommended envelope (RFC 7807-inspired)

{
  "type": "https://api.dashnote.example/errors/not-found",
  "title": "Not Found",
  "status": 404,
  "code": "note_not_found",
  "detail": "Note 42 does not exist in this workspace",
  "instance": "/notes/42",
  "request_id": "01H..."
}

Status discipline

StatusMeaning for API designers
400Malformed or semantically invalid request you won’t retry as-is
401Missing/invalid auth
403Authenticated but not allowed
404Missing — or hide existence (cross-tenant)
409Conflict (duplicate, version mismatch)
422Validation failed (schema/field level)
429Rate limited — include Retry-After
500/502/503Your problem / dependency / temporary — retry policy differs
DashNote · Partial
FastAPI {"detail": "..."} + default 422 + global 500. SSE uses in-band {"type":"error"}. Cross-tenant threads intentionally 404. Should be: shared error model + request_id on every error.

08 Idempotency

Networks retry. Without idempotency, retries create duplicate notes, charges, and emails.

Idempotency-Key pattern

  1. Client sends Idempotency-Key: <uuid> on POST/PATCH that must not double-apply
  2. Server stores key → response (or in-flight lock) scoped to user/tenant
  3. Replay with same key + same body → same status + body
  4. Same key + different body → 409 conflict
  5. TTL keys (e.g. 24h); document retention

What must be idempotent

  • Payments, invites, provisioning, “send email”, webhook handlers
  • Any create that clients will retry on timeout
  • Worker side effects (upsert by natural key) — necessary but not a substitute for HTTP keys
DashNote · Gap (HTTP) / Partial (workers)
No Idempotency-Key middleware. Workers upsert embeddings (ops-idempotent). Attach-to-note is DB-safe on retry. Should be: keys on create note/upload/invite and any future billing webhook ingress.

09 Sync RPC vs async job + status

If work can exceed a few seconds or depends on flaky systems, don’t hold the HTTP request hostage.

Stay sync when

  • Work is < ~1–2s p95
  • Client needs the result to continue UI
  • Failure should fail the request

Go async when

  • Embedding, OCR, video, big exports
  • Fan-out to many systems
  • You need retries without blocking the user

Async API patterns

PatternResponseClient next step
202 + job resource 202 Accepted + /jobs/{id} Poll status until terminal
200 + side effect Resource created; indexing later Poll resource field or search readiness
Webhook callback 202; notify later Receive event at client URL
SSE / WebSocket Open stream Consume progress events 
// Recommended job status shape
{
  "id": "job_123",
  "type": "embed_note",
  "status": "queued" | "running" | "succeeded" | "failed",
  "progress": 0.4,
  "result": { "note_id": "42" },
  "error": null,
  "created_at": "...",
  "updated_at": "..."
}
DashNote · Partial
POST /notes/ returns the note immediately and enqueues embed_note_task (never blocks on enqueue failure). File upload emits events similarly. No 202 / /jobs/{id}. Should be: expose indexing status (on note/file or job resource) so clients don’t guess “~45s”.

10 Webhook delivery

Webhooks push domain events to customer endpoints. Design them like a public API.

  • Sign payloads (HMAC) with timestamp; reject skew
  • At-least-once delivery — receivers must be idempotent
  • Retry with backoff + dead-letter after N failures
  • Event schema version in payload or envelope
  • Minimal PII; prefer IDs + fetch pattern when sensitive
  • Outbound allowlist / SSRF guards if users supply URLs
{
  "id": "evt_01H...",
  "type": "note.created",
  "api_version": "v1",
  "created_at": "2026-07-18T12:00:00Z",
  "data": { "note_id": "42", "workspace_id": "7" }
}
DashNote · Gap
Internal event bus + ARQ only — no customer webhook ingress/egress. Should be: when integrations land, ship signed delivery + retries before the first partner depends on you.

11 Streaming APIs

Streaming is still an API contract — event types, errors, and termination rules matter.

SSE

One-way server→client over HTTP. Great for tokens/progress. Simple auth via header/cookie.

WebSocket

Bidirectional. Presence, collab, multiplexed rooms. Heavier ops story.

  • Document event schema (token, message, error, done)
  • How errors appear: HTTP before stream opens vs in-band events
  • Heartbeat / comment lines to keep proxies alive
  • Proxy headers: disable buffering (X-Accel-Buffering: no)
DashNote · Covered
POST /ai/chat/stream and agent SSE with text/event-stream + Nginx-friendly headers. Treat stream event types as versioned contract the same way as JSON routes.

12 Auth in the API contract

AuthN/Z deep-dive is a separate roadmap topic — but the API must advertise how access works.

  • Document schemes: Bearer JWT, API keys, cookies, mTLS
  • Which routes are public vs authenticated
  • 401 vs 403 vs 404 for authorization failures (enumeration policy)
  • Scopes / roles in token claims vs server-side lookups
  • Login endpoints get stricter rate limits
DashNote · Covered
/auth/register|login|refresh|logout, Bearer JWT with wid+role, RBAC on mutations, dedicated login rate limit. OpenAPI security schemes when docs enabled.

13 Rate limits as part of the contract

Clients need to know budgets — not discover them via random 429s.

  • Document limits per IP / user / tenant / route class
  • Return 429 + Retry-After (and optionally X-RateLimit-*)
  • Separate expensive routes (login, AI, upload) from CRUD budgets
  • Fail-open vs fail-closed when the limiter store is down — pick consciously
DashNote · Covered
Nginx 10 r/s + Redis app 100/min global + login 5/min; Retry-After on 429. Should be: publish limits in docs/OpenAPI description; optional remaining headers for clients.

14 Evolution & deprecation

APIs outlive features. Plan change like a release train.

Compatible (usually safe)

  • Add optional request fields / new response fields
  • Add new endpoints or enum values clients can ignore
  • Relax validation (accept more)

Breaking (needs version or migration)

  • Remove/rename fields; change types or status codes
  • Make optional fields required; tighten validation
  • Change auth scheme or error envelope

Deprecation playbook

  1. Announce in changelog + Deprecation / Sunset headers
  2. Dual-run old+new behavior when possible
  3. Metrics on old endpoint usage
  4. Remove only after traffic dies or date passes

15 REST · RPC · GraphQL — choose deliberately

StyleBest forWatch-outs
REST resources CRUD products, caching, wide client ecosystems Over/under-fetch; chatty lists
RPC (JSON/gRPC) Actions, internal services, strict schemas, streaming RPC Easy to invent a method swamp
GraphQL Flexible BFF for complex UIs AuthZ per field, caching, N+1, complexity limits
Guideline
One public style per product surface. DashNote’s public shape is REST + a few RPC-like POSTs (/ai/chat) + SSE — that mix is fine if documented. Don’t add GraphQL “because modern” without a BFF pain.

16 OpenAPI & contract workflow

The machine-readable contract is how FE, mobile, and partners stay honest.

  • Code-first (FastAPI/Nest decorators) or design-first (OpenAPI → codegen)
  • CI: breaking-change detection on openapi.json diffs
  • Examples for happy path + 4xx
  • Security schemes, servers, rate-limit notes in description
  • Keep human tutorial docs in sync (docs/user.md style)
DashNote · Covered (dev) / Should harden
/docs, /redoc, /openapi.json when DEBUG; disabled in prod (good). Human smoke flow in docs/user.md. Should be: export OpenAPI in CI for contract tests even when prod docs are off.

18 Code examples TOGGLE

FastAPI matches DashNote. NestJS is the TypeScript parallel for the same contracts.

1. Resource CRUD + PATCH semantics

Create · read · patch 
# FastAPI — mirrors notes/schemas.py + router style
from pydantic import BaseModel
from fastapi import APIRouter, HTTPException

class NoteCreate(BaseModel):
    title: str
    content: str
    is_private: bool = False

class NoteUpdate(BaseModel):
    title: str | None = None
    content: str | None = None
    is_private: bool | None = None

class NoteRead(BaseModel):
    id: int
    title: str
    content: str
    is_private: bool
    created_by: int
    class Config:
        from_attributes = True

router = APIRouter(prefix="/notes", tags=["notes"])

@router.post("/", response_model=NoteRead, status_code=201)
async def create_note(data: NoteCreate): ...

@router.patch("/{note_id}", response_model=NoteRead)
async def update_note(note_id: int, data: NoteUpdate):
    note = await repo.get(note_id)
    if not note:
        raise HTTPException(404, detail="Note not found")
    # apply only fields that were sent (exclude_unset)
    await repo.update(note, data.model_dump(exclude_unset=True))
    return note
// NestJS — same contract
import { IsBoolean, IsOptional, IsString } from 'class-validator';
import { Body, Controller, Param, Patch, Post } from '@nestjs/common';

export class NoteCreateDto {
  @IsString() title: string;
  @IsString() content: string;
  @IsBoolean() @IsOptional() is_private?: boolean = false;
}
export class NoteUpdateDto {
  @IsString() @IsOptional() title?: string;
  @IsString() @IsOptional() content?: string;
  @IsBoolean() @IsOptional() is_private?: boolean;
}

@Controller('notes')
export class NotesController {
  @Post()
  create(@Body() dto: NoteCreateDto) { return this.notes.create(dto); }

  @Patch(':id')
  update(@Param('id') id: string, @Body() dto: NoteUpdateDto) {
    return this.notes.update(+id, dto); // service applies defined fields only
  }
}

2. Paginated list envelope

skip / limit / total 
# FastAPI — extend files pattern to all collections
from fastapi import APIRouter, Query
from pydantic import BaseModel, Field

class NoteRead(BaseModel):
    id: int
    title: str

class NoteListResponse(BaseModel):
    items: list[NoteRead]
    total: int
    skip: int
    limit: int

router = APIRouter(prefix="/notes")

@router.get("/", response_model=NoteListResponse)
async def list_notes(
    skip: int = Query(0, ge=0),
    limit: int = Query(20, ge=1, le=100),
    sort: str = Query("-created_at"),
):
    rows, total = await repo.list(skip=skip, limit=limit, sort=sort)
    return NoteListResponse(items=rows, total=total, skip=skip, limit=limit)
// NestJS
import { Controller, Get, Query, DefaultValuePipe, ParseIntPipe } from '@nestjs/common';

@Controller('notes')
export class NotesController {
  @Get()
  list(
    @Query('skip', new DefaultValuePipe(0), ParseIntPipe) skip: number,
    @Query('limit', new DefaultValuePipe(20), ParseIntPipe) limit: number,
    @Query('sort') sort = '-created_at',
  ) {
    const safeLimit = Math.min(Math.max(limit, 1), 100);
    return this.notes.list({ skip, limit: safeLimit, sort });
    // → { items, total, skip, limit }
  }
}

3. Idempotency-Key on create

Should-be write safety 
# FastAPI — store key → response in Redis (tenant-scoped)
from fastapi import Header, HTTPException, Request

@router.post("/", response_model=NoteRead, status_code=201)
async def create_note(
    data: NoteCreate,
    request: Request,
    idempotency_key: str | None = Header(default=None, alias="Idempotency-Key"),
):
    if idempotency_key:
        cached = await idem.get(ctx.workspace_id, idempotency_key)
        if cached:
            if cached.body_hash != hash_body(data):
                raise HTTPException(409, detail="Idempotency key reuse with different body")
            return cached.response  # same status/body
        lock = await idem.acquire(ctx.workspace_id, idempotency_key)
        if not lock:
            raise HTTPException(409, detail="Request in progress for this key")

    note = await repo.create(...)
    if idempotency_key:
        await idem.put(ctx.workspace_id, idempotency_key, note, ttl=86400)
    return note
// NestJS — interceptor or guard reads Idempotency-Key
import { Headers, Post, Body, ConflictException } from '@nestjs/common';

@Post()
async create(
  @Body() dto: NoteCreateDto,
  @Headers('idempotency-key') key?: string,
) {
  if (key) {
    const cached = await this.idem.get(this.tenantId, key);
    if (cached) {
      if (cached.bodyHash !== hash(dto)) {
        throw new ConflictException('Idempotency key reuse with different body');
      }
      return cached.response;
    }
  }
  const note = await this.notes.create(dto);
  if (key) await this.idem.put(this.tenantId, key, note, 86_400);
  return note;
}

4. Async job: 202 + status endpoint

Long work without blocking 
# FastAPI — alternative to fire-and-forget-only
from fastapi import APIRouter
from fastapi.responses import JSONResponse

@router.post("/notes/{note_id}/reindex", status_code=202)
async def reindex(note_id: int):
    job_id = await jobs.enqueue("embed_note_task", note_id=note_id)
    return JSONResponse(
        status_code=202,
        content={"job_id": job_id, "status": "queued"},
        headers={"Location": f"/jobs/{job_id}"},
    )

@router.get("/jobs/{job_id}")
async def job_status(job_id: str):
    job = await jobs.get(job_id)
    if not job:
        raise HTTPException(404, detail="Job not found")
    return job  # status, progress, result, error
// NestJS
import { Controller, Post, Get, Param, Res, HttpStatus } from '@nestjs/common';
import { Response } from 'express';

@Controller()
export class JobsController {
  @Post('notes/:id/reindex')
  async reindex(@Param('id') id: string, @Res() res: Response) {
    const jobId = await this.jobs.enqueue('embed_note_task', { noteId: id });
    res.setHeader('Location', `/jobs/${jobId}`);
    return res.status(HttpStatus.ACCEPTED).json({ job_id: jobId, status: 'queued' });
  }

  @Get('jobs/:id')
  status(@Param('id') id: string) {
    return this.jobs.get(id); // 404 if missing
  }
}

5. Structured errors

Stable error code envelope 
# FastAPI — shared exception → problem-style JSON
from fastapi import FastAPI, Request
from fastapi.responses import JSONResponse

class AppError(Exception):
    def __init__(self, status: int, code: str, detail: str):
        self.status, self.code, self.detail = status, code, detail

app = FastAPI()

@app.exception_handler(AppError)
async def app_error_handler(request: Request, exc: AppError):
    return JSONResponse(
        status_code=exc.status,
        content={
            "title": exc.code,
            "status": exc.status,
            "code": exc.code,
            "detail": exc.detail,
            "instance": str(request.url.path),
            "request_id": request.headers.get("x-request-id"),
        },
    )

# raise AppError(404, "note_not_found", "Note 42 does not exist")
// NestJS — filter for stable error shape
import { Catch, ExceptionFilter, ArgumentsHost, HttpException } from '@nestjs/common';
import { Response, Request } from 'express';

export class AppError extends HttpException {
  constructor(status: number, public code: string, detail: string) {
    super({ code, detail }, status);
  }
}

@Catch(AppError)
export class AppErrorFilter implements ExceptionFilter {
  catch(exc: AppError, host: ArgumentsHost) {
    const ctx = host.switchToHttp();
    const res = ctx.getResponse<Response>();
    const req = ctx.getRequest<Request>();
    const status = exc.getStatus();
    res.status(status).json({
      title: exc.code,
      status,
      code: exc.code,
      detail: (exc.getResponse() as any).detail,
      instance: req.path,
      request_id: req.headers['x-request-id'],
    });
  }
}

19 Mastery checklist

Check when you can design and defend the decision — with or without looking at DashNote.

Foundations

  • State the 6 design principles in your own words
  • Model a new domain as resources (flat vs nested vs action)
  • Map safe / unsafe / idempotent methods correctly
  • Split Create / Update / Read DTOs and PATCH null semantics

Contracts

  • Choose a versioning strategy and compatibility promise
  • Design a list envelope with pagination + allowlisted sort/filter
  • Specify a stable error envelope (status, code, detail, request_id)
  • Explain Idempotency-Key lifecycle (store, conflict, TTL)
  • Decide sync vs 202-job vs webhook vs SSE for a slow feature
  • Sketch a signed webhook event + retry policy

Hardening

  • Document auth scheme + 401/403/404 enumeration policy
  • Treat rate limits as published contract
  • Classify a change as compatible vs breaking + deprecation steps
  • Pick REST vs RPC vs GraphQL for a given product surface
  • Wire OpenAPI into CI for breaking-change detection

DashNote gaps you can name

  • Uniform pagination beyond files
  • Shared errors + request_id
  • Idempotency-Key on writes
  • Job/indexing status visibility
  • API versioning before external lock-in
