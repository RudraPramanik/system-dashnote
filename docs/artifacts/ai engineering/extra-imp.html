01 Why Tier 4 exists

Independent builders need Tiers 1–3 first: models/tokens, retrieval, agents, prompts, evals, security, reliability. Tier 4 is the “you’ll bump into these” layer — useful vocabulary and decision frames, not day-one blockers.

Learn now for judgment

So you don’t rebuild Qdrant, ignore feedback loops, or bolt vision on before text RAG is solid.

Don’t block shipping

DashNote already works without multimodal or A2A. Summarization and integrate-first LLM wiring are partial / done.

02 Build vs Integrate core habit

Default: integrate undifferentiated heavy lifting; build the thin layer that encodes your product laws (tenancy, RBAC, events, prompts).

Integrate when…

  • Commodity capability (embeddings, LLM, vector search)
  • Provider can be swapped via config
  • Ops burden > differentiation
  • You need speed to learn product fit

Build when…

  • Tenant isolation / RBAC must be yours
  • Domain events & workflows are the product
  • Contracts must stay stable across providers
  • Compliance / audit path is custom

DashNote’s actual split

LayerChoiceWhy
LLM + embeddings Integrate LiteLLM Prefix-routed providers (gemini/, nvidia_nim/); keys in settings
Vectors Integrate Qdrant Soft-boot; own wrapper WorkspaceVectorSearch + RBAC filter
Agent runtime Integrate LangGraph Checkpointer + ToolNode; own tools/services
Tracing Integrate Langfuse Via observability.tracing only — no SDK in ai/*
Storage Integrate local / MinIO / R2 get_storage() behind interface
Parsing Thin build FileParsingEngine on pypdf / docx / bs4 — not Unstructured
Tenancy, events, RAG, tools Build Product core — never outsource workspace_id / RBAC
Rule of thumb
Integrate the atom (model call, vector upsert). Build the molecule (IndexingRequest, emit_event, RagService, NoteService tools).

03 Data Flywheel partial

A data flywheel is a closed loop: product usage creates data → data improves models/retrieval/UX → better product → more usage. Without the feedback edge, you only have a pipeline.

1 · USEUsers create notes / upload files
2 · CAPTUREExtract · embed · tag · summarize
3 · LEARNSignals: clicks, thumbs, edits, evals
4 · IMPROVEBetter ranking, prompts, tools

Pipeline ≠ flywheel

upload→ extract→ index→ metadata→ RAG/agent ··· no feedback yet
  • Event bus: FileUploadedEvent / NoteCreatedEvent → ARQ fan-out
  • Embeddings cached in Redis (embed:v1:…)
  • Auto tags + file summary enrich the corpus
  • Langfuse traces for LLM spans (when keys set)
  • User thumbs up/down on chat answers
  • Citation click / copy events → re-rank training or eval sets
  • Golden Q&A sets refreshed from real failures
  • Prompt / chunk-size experiments driven by those metrics
  • Log chunks_used + answer id; store optional rating row
  • Weekly offline eval on fixed fixtures (see evals guide)
  • Promote high-rated Q→A pairs into few-shot or regression tests
Privacy
Flywheels amplify tenant data. Keep signals scoped by workspace_id; never train global models on raw notes without explicit product policy.

Quiz · Is it a flywheel?

File upload → extract → summary → Qdrant. Users never rate answers.

04 Summarization shipped (partial depth)

Compress long content into a shorter artifact humans or downstream agents can use. Pick extractive (keep sentences) vs abstractive (rewrite) vs hierarchical / map-reduce (chunk → local summaries → global).

Extractive

Select key sentences. Faithful, dull, cheap.

Abstractive

LLM rewrite. Readable; risk of drift — use structured schema.

Map-reduce

Per-chunk then merge. Needed when context > budget.

Where DashNote summarizes today

SurfacePathShape
File metadata generate_file_metadata Abstractive 2–4 sentences + tags via acompletion_structured → files.summary
Workspace digest summarize_workspace tool RAG with retrieval_limit=12 — broad overview, not map-reduce
Note tags generate_note_tags Not a summary — topical labels only
Chat / agent User asks “summarize…” Ad-hoc via RAG or tools — no dedicated note.summary column
Auto-summarize / auto-tag are non-destructive — AutomationDecisionEngine is skipped (rules.md). Destructive automation (merge/delete) must go through governance.
File metadata already truncates document context for the LLM. For workspace-wide digests on large tenants, prefer map-reduce or “summary of summaries” over stuffing 12 raw chunks forever.

Quiz · Which summarizer?

A PDF uploads and must get a short blurb stored on the File row without user action.

05 Multimodal not yet

Models (or pipelines) that accept more than text: images, audio, video, tables-as-pixels. For notes products this usually means: vision for screenshots/scans, OCR for PDFs that are images, optional speech-to-text for voice notes.

Approach A · Native multimodal LLM

Send image bytes + prompt to a vision model. Simple path; cost & latency higher; harder to cache embeddings for search.

Approach B · Unimodal bridge

OCR / ASR → text → existing DashNote chunk → embed → RAG. Reuses Slice 1–7. Better for search; OCR quality is the bottleneck.

Current upload surface (text-ish only)

ALLOWED_MIME_TYPES ⊂ {
  pdf, doc/docx, xls/xlsx, ppt/pptx, txt, csv
}
# No image/*, audio/*, video/*
FileParsingEngine → text only (pypdf / docx / bs4)
Don’t rush
Multimodal expands attack surface (prompt injection in images) and cost. Ship solid text RAG + file summaries first — Tier 4, not Tier 1.

06 A2A Protocol not yet

Agent-to-Agent (A2A) is an open protocol (popularized by Google’s A2A effort) for agents from different systems to discover each other, negotiate tasks, and exchange messages/artifacts — without sharing internal tools or memory.

Not the same as MCP
MCP = tools/resources for one agent (host ↔ servers). A2A = peer agents collaborating across products. DashNote already has internal tools (LangGraph); A2A would be external peers.

Mental model

Agent Card→ discover→ task→ messages / artifacts→ status
  • Workspace assistant talks to a calendar agent or CRM agent owned elsewhere
  • Standard task lifecycle instead of one-off webhooks
  • Capability advertising without exposing your Postgres / Qdrant
  • Today: one LangGraph workspace assistant + in-process StructuredTools
  • A2A: remote agents as peers; auth, discovery, and trust boundaries
  • Keep /ai/chat* fast RAG and /ai/agent* local tools — A2A would be additive
  • You have ≥2 production agents that must collaborate across repos/companies
  • Partners demand a standard handshake
  • Not needed for “search my notes and create a note” inside one backend

Quiz · MCP or A2A?

Your agent needs a GitHub “create issue” capability as a tool.

08 Implement in DashNote

Ordered by leverage — stay append-only on settings; keep import laws.

  1. Keep integrate-first for models

    New providers = LiteLLM model string + env key in settings / shared/llm/env.py. Do not fork provider SDKs into ai/*.

  2. Close a thin flywheel loop

    Add optional POST /ai/feedback (thread_id, message_id, rating, note). Persist workspace-scoped rows. Nightly job: export low ratings into an eval fixture folder. Improve prompts/chunking from that set — not from raw dumps.

  3. Deepen summarization when needed

    If workspace digests miss content: map-reduce over note titles + existing files.summary first (cheap), then fall back to chunk RAG. Optional: notes.summary column + worker on note.updated (non-destructive).

  4. Multimodal via text bridge

    Extend ALLOWED_MIME_TYPES carefully → new extract path (OCR or vision → string) → same extracted_text + fan-out. Reuse index_file_chunks / generate_file_metadata. Gate vision model behind settings; soft-fail like Qdrant.

  5. Defer A2A

    Until a real peer agent exists, expand local tools (files search, attachments) and MCP-style tool servers if needed. If A2A arrives: adapter service outside ai/* core, JWT/workspace auth intact, never leak tenant vectors.

09 Checklist

Learning + build tracker (localStorage).

Understand

  • Integrate commodities; build tenant/product laws
  • Pipeline ≠ flywheel without feedback → improve
  • Extractive vs abstractive vs map-reduce summaries
  • Multimodal: native vision vs OCR→text bridge
  • A2A peers ≠ MCP tools ≠ LangGraph ToolNode

Build next (priority)

  • Optional chat answer rating + workspace-scoped store
  • Eval fixtures fed by down-rated answers
  • Map-reduce / summary-of-summaries for large digests
  • (Later) image MIME + OCR/vision → extracted_text
  • (Much later) A2A adapter only with a real peer
