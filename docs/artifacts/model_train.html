Model training — know it, rarely own it

Important if you create or fine-tune foundation models. For DashNote and most product engineers: start with hosted APIs; treat training as a later lever after retrieval, prompts, and evals are exhausted.

Training Pretraining Post-training RLHF API-first

01 Why this matters (and why not yet)

Labs spend millions on pretraining and alignment. Product apps usually rent the result via an API. You still need the vocabulary to choose models, read release notes (“SFT + DPO”), and know when fine-tuning is the wrong fix.

02 Training basics concepts only

Training updates model weights from data so loss decreases. At LLM scale that means gradient descent on huge corpora (pretrain) or smaller curated sets (post-train). Inference (what DashNote does) only reads weights.

Training

  • Forward → loss → backward → optimizer step
  • Needs GPUs, checkpoints, data pipelines
  • Changes the model itself

Inference (DashNote)

  • LiteLLM acompletion / embeddings
  • Frozen provider weights
  • Behavior steered by prompts, tools, RAG

Loss types you’ll hear

ObjectiveUsed inIntuition
Next-token CE Pretrain, often SFT “Predict the next token given context”
Preference / ranking RLHF, DPO “Prefer answer A over B”
Reward model Classic RLHF Score completions; policy maximizes score

Update (almost) all weights. Max capacity, max cost. Rare for apps; labs and large FT jobs.

LoRA / QLoRA: train small adapter matrices; freeze base. Cheapest realistic path if DashNote ever fine-tunes style or tool-calling format.

Prompts, RAG, and few-shot change behavior without weight updates. Prefer these until evals prove a systematic gap that data + FT can close.

03 Pretraining not DashNote

Train a base model from random (or prior) init on massive unlabeled text (and sometimes code/multimodal). Goal: general next-token competence — grammar, facts, reasoning patterns — not “be a helpful assistant” yet.

web / books / code→ tokenize · pack→ causal LM loss→ base checkpoint

What you get

  • Broad world knowledge (stale by cutoff)
  • In-context learning ability
  • Not instruction-tuned by default

What you don’t

  • Reliable JSON / tool schemas
  • Your workspace notes (not in corpus)
  • Safe refusal policies
Product truth
Workspace knowledge belongs in retrieval + memory, not in pretraining. Notes change hourly; base weights don’t.

04 Post-training API models already have it

Everything after the base checkpoint that makes a model usable as a product: instruction following, chat format, tool calling, safety. Collectively post-training (sometimes “alignment” for the preference part).

SFT

Supervised fine-tune on (prompt, ideal completion) pairs. Teaches format, tone, tool call JSON.

Preference

RLHF, DPO, ORPO, … — learn from A≻B rankings without (or with less) RL.

Domain FT

Extra SFT/LoRA on your domain examples. What a product might do later — not pretraining.

05 RLHF & preference methods labs / providers

RLHF (Reinforcement Learning from Human Feedback): humans rank outputs → train a reward model → optimize the policy (often PPO) to maximize reward while staying close to the SFT model (KL penalty).

SFT model→ sample pairs→ human ranks→ reward model→ RL (PPO)→ aligned chat model
  • Expensive: raters, RM training, unstable RL
  • Strong for open-ended chat preference
  • What frontier “assistant” models already went through
  • DPO: preference pairs → closed-form update; no separate RM/RL loop
  • ORPO, KTO, IPO — same family of ideas
  • Easier ops; still needs high-quality preference data
  • Thumbs up/down on answers ≈ preference data seed
  • Use first for evals and prompt iteration, not PPO
  • Only later: curated pairs → hosted preference FT (if ever)
Don’t confuse
AutomationDecisionEngine is a runtime governance gate, not RLHF. It scores one proposed action with a structured LLM call — no reward model training.

06 When to fine-tune (decision tree)

For independent builders: default no. Climb the cheaper ladder first.

  1. Prompt + schema + few-shot

    Cheapest. DashNote automation & RAG prompts live here today.

  2. Retrieval / chunking / ranking

    Most “model is dumb” bugs are missing context. Fix Qdrant quality gates.

  3. Swap model via LiteLLM

    Change LLM_MODEL / embedding model; keep contracts. Measure with evals.

  4. Hosted SFT / LoRA (later)

    Only if evals show stable format/style failures across strong models + good RAG.

  5. Preference FT / RLHF

    Almost never for a notes MVP. Leave to labs unless you become a model vendor.

  6. Pretraining

    Out of scope forever for DashNote.

08 Implement later in DashNote

Do not start this now. When evals force your hand, stay hosted and append-only — never train inside the API process.

  1. Prove the gap with evals

    Fixed fixtures: refuse-without-context, cite real chunk ids, tool trajectories, tag JSON parse rate. FT only if ≥2 strong API models fail the same suite after prompt/RAG work.

  2. Collect training-ready data (privacy first)

    Opt-in / synthetic / anonymized (prompt, completion) or preference pairs. Never dump raw multi-tenant notes into a vendor FT upload without policy, redaction, and workspace consent.

  3. Hosted SFT or LoRA job

    Upload JSONL to provider fine-tuning API → receive ft:… model id. Point LLM_MODEL (or a new LLM_MODEL_FT) at it via LiteLLM. Keep RAG/embeddings on the general model unless evals say otherwise.

  4. Shadow deploy

    Route a % of traffic or a feature flag workspace to the FT model; compare Langfuse + offline scores; easy rollback = change one setting.

  5. Skip RLHF in-house

    If preferences matter, use provider preference-FT / DPO offerings — or keep iterating prompts. Building PPO + RM is a research org, not a notes backend.

09 Checklist

Learning tracker — build items are explicitly later.

Understand

  • Training updates weights; inference does not
  • Pretrain = base capability from huge unlabeled data
  • Post-train = SFT + preference (RLHF/DPO/…)
  • RLHF classic ≠ DPO; both need preference data
  • Private notes → RAG, not pretraining
  • Climb: prompt → retrieve → swap model → then FT

Later (only if evals demand)

  • Offline eval suite proves systematic gap
  • Privacy-safe JSONL / preference dataset
  • Hosted SFT/LoRA → LLM_MODEL_FT behind flag
  • Shadow traffic + rollback via settings
  • Explicitly skip in-house RLHF
