Concurrency & Load Balancing

How two requests collide — and how traffic finds a healthy instance. Races, locks, unique constraints, then L4/L7, sticky sessions (and why not), CDN, TLS.

00 Overview

Concurrency is “two writers, one truth.” Load balancing is “many servers, one hostname.” Get the first wrong and you corrupt data. Get the second wrong and you create sticky hell or uneven load.

Part 11 · Concurrency & locking

01 Race conditions — plain English

A race is when the result depends on timing. Two requests both “check then act” and both think they won.

Classic TOCTOU

Time Of Check → Time Of Use:

  1. A: “Is email free?” → yes
  2. B: “Is email free?” → yes
  3. A inserts · B inserts → duplicate or 500

Fix patterns

  • Unique constraint + catch conflict → 409
  • Atomic upsert / ON CONFLICT
  • Row lock or version check on update
  • Idempotency-Key on POST
Mental model
Application “if” checks are advice. The database constraint is law. Design so the law wins even when two pods race.
DashNote · Partial
Register is one DB transaction. Membership is check-then-insert + composite PK — a race can still raise unhandled IntegrityError. Page versions: max(version)+1 without lock (src/pages/versioning.py) — two editors can collide. Notes: last-write-wins on update.

02 Optimistic vs pessimistic locking

Two ways to serialize writers. Pick based on conflict rate, not fashion.

Optimistic

Assume conflicts are rare. Read a version; write only if it still matches.

  • UPDATE … WHERE id=? AND version=?
  • 0 rows → 409 Conflict / retry
  • Also: ETag / If-Match on HTTP

Best for: collaborative notes, profiles, settings.

Pessimistic

Assume you must own the row. SELECT … FOR UPDATE blocks others until commit.

  • Holds a DB lock for the transaction
  • Can deadlock if lock order is wrong
  • Increases latency under contention

Best for: inventory, money transfer, “append next version” under load.

OptimisticPessimistic
Conflict rare Great — cheap Overkill
Conflict common Many retries / 409s Serialized, predictable
Long “think time” OK (edit form, then save) Bad (holds lock while user types)
Failure mode Client retries or merges Wait / timeout / deadlock
Don’t lock while waiting on the network
Never hold FOR UPDATE across an LLM call or S3 upload. Lock → mutate → commit → then call out.
DashNote · Gap
updated_at is audit only — not used for CAS. No version column / ETag / with_for_update in app code. Should be: optimistic version on note/page edits; UNIQUE + retry or FOR UPDATE on page version append.

03 Unique constraints as correctness tools

A unique index is the cheapest distributed lock you’ll ever love. The database refuses the second writer — atomically, across all replicas of your app.

Natural unique

Email, username, storage_key, invite token.

Composite unique

(page_id, version), (user_id, workspace_id) membership.

Idempotent write

ON CONFLICT DO NOTHING / upsert — second call is a no-op.

  • Always map IntegrityError / unique violation → 409 with a clear message.
  • Prefer unique + conflict over “SELECT then INSERT” alone.
  • UUID in the key (upload paths) reduces collision probability — unique still seals it.
DashNote · Partial / strong examples
users.email unique · files.storage_key unique · note–file link ON CONFLICT DO NOTHING (src/files/repository.py). Missing: UNIQUE(page_id, version); invite race → handle IntegrityError.

04 Distributed locks — when to avoid them

A Redis SET key NX EX lock coordinates work across processes. It’s easy to get subtly wrong (forgotten unlock, TTL too short, lock stolen).

Prefer instead

  • Unique constraints / upserts
  • Idempotent handlers + job IDs
  • Single-consumer queue per partition
  • Optimistic versioning

OK to use when

  • Exactly one cron must run cluster-wide
  • Leader election for a singleton worker
  • Short critical section with safe TTL + token
Lock dangers
1) Unlock someone else’s lock (always compare a random token) · 2) TTL expires mid-work → two holders · 3) Process dies holding lock · 4) Using locks to “fix” non-idempotent business logic.
DashNote · Covered (avoided) — good
No Redis Redlock / SET NX for business ops. Only in-process asyncio.Lock for singleton client init (embeddings/Qdrant). Keep it that way; lean on DB uniqueness and upserts.

Part 13 · Load balancing & edge

05 L4 vs L7 — easy picture

Layer 4 balances TCP/UDP connections (IP + port). It doesn’t read HTTP. Layer 7 understands HTTP — path, host, headers, cookies.

L4 (transport)L7 (application)
Sees IPs, ports, TCP streams URLs, headers, cookies, gRPC
Speed / cost Very fast, cheap Slightly more CPU; smarter
Routing Whole connection → one backend /api vs /static; A/B; auth gate
Examples NLB, HAProxy TCP, cloud LB TCP Nginx, ALB, Envoy, Cloudflare
TLS Often pass-through (or terminate) Usually terminates TLS, can re-encrypt
Rule of thumb
APIs and websites → L7. Raw databases / game sockets / extreme QPS → often L4. DashNote’s Nginx is classic L7 HTTP reverse proxy.
DashNote · Partial
nginx/default.conf: HTTP reverse proxy to api_upstream, one peer api:8000, keepalive 32, forward headers + request id. Algorithm N/A until you add more servers (then default round-robin).

06 Round-robin · least-conn · consistent hashing

How the LB picks the next backend. All assume health checks remove sick peers.

Round-robin

1, 2, 3, 1, 2… Simple default. Fine when requests cost about the same.

Least connections

Send to the backend with fewest open conns. Better for slow/uneven work (uploads, LLM).

Consistent hashing

Hash a key (user id, cache key) → same backend often. Good for local caches; bad if that pod dies mid-session without shared state.

  • Weighted variants: bigger machines get more traffic (canaries, mixed sizes).
  • Health-aware > clever algorithm — don’t send traffic to a dying pod.
  • Use readiness (not liveness) for “in the pool.”
DashNote · Should be
Multi-server upstream (or Docker DNS to N replicas). Stay sticky-free. Prefer least-conn if LLM routes are slow and share the same pool as CRUD.

07 Sticky sessions — and why to avoid them

Sticky (session affinity / ip_hash / cookie) pins a client to one backend. It papers over in-memory session state — and creates new problems.

Why people use sticky

  • Server stores session in RAM
  • WebSocket “must” hit same node
  • Local cache warmer on one box

Why to avoid

  • Uneven load (one loud user → one hot pod)
  • Deploys / crashes drop “their” sessions
  • Harder autoscaling and canaries
Better design
Stateless API (JWT) + shared Redis for anything that must survive a pod swap. WebSockets: sticky or a pub/sub bus so any node can push.
DashNote · Covered (sticky avoided)
No ip_hash. JWT access tokens validate on any replica; refresh/blacklist need Redis for multi-instance. Keep it that way when you scale the API.

08 CDN for static assets · TLS termination

Put the edge where users are. Terminate HTTPS once at a trusted front door, then talk HTTP (or mTLS) to your origin inside the private network.

CDN (content delivery network)

  • Caches static assets (JS, CSS, images) at PoPs near users.
  • Use long Cache-Control + fingerprinted filenames (app.abc123.js).
  • APIs with auth are usually not CDN-cached (or only public GETs with care).
  • Blobs: public CDN URL or short-lived signed URL from R2/S3.

TLS termination

BrowserHTTPS Edge (CF / Caddy / ALB)HTTP Nginx / API
  • Terminate at edge — certificates live in one place; origin stays simple.
  • Set X-Forwarded-Proto so the app knows the client used HTTPS.
  • Prod: HTTP→HTTPS redirect; prefer Full (Strict) to origin if re-encrypting.
DashNote · Partial / Gap
Covered: edge limit_req 10r/s + app Redis limits; proxy headers; ProxyHeadersMiddleware. Gap: listen :80 only; no CDN in compose; TLS planned via Cloudflare/Caddy (docs/documentation/production.md). Files: app download or R2 presign — not a CDN yet.

10 Code examples TOGGLE

FastAPI matches DashNote. NestJS uses TypeORM / Prisma and similar HTTP patterns.

1. Optimistic locking (version column)

CAS update · 409 on conflict 
# FastAPI / SQLAlchemy — should-be for note edits
@router.patch("/notes/{note_id}")
async def update_note(note_id: int, body: NoteUpdate, db: AsyncSession):
    result = await db.execute(
        update(Note)
        .where(Note.id == note_id, Note.version == body.version)
        .values(title=body.title, content=body.content, version=Note.version + 1)
        .returning(Note)
    )
    note = result.scalar_one_or_none()
    if note is None:
        raise HTTPException(409, "Note was updated elsewhere — refresh and retry")
    await db.commit()
    return note
// NestJS — TypeORM @VersionColumn or manual
@Patch(":id")
async update(@Param("id") id: string, @Body() body: UpdateNoteDto) {
  const r = await this.repo.update(
    { id, version: body.version },
    { title: body.title, content: body.content, version: body.version + 1 },
  );
  if (!r.affected) {
    throw new ConflictException("Note was updated elsewhere — refresh and retry");
  }
  return this.repo.findOneByOrFail({ id });
}

2. Unique constraint + IntegrityError → 409

DB is the lock · app maps the error 
# FastAPI — register / invite race
from sqlalchemy.exc import IntegrityError

async def add_member(db: AsyncSession, user_id: int, workspace_id: int):
    db.add(Membership(user_id=user_id, tenant_id=workspace_id))
    try:
        await db.commit()
    except IntegrityError:
        await db.rollback()
        raise HTTPException(409, "Already a member of this workspace")
// NestJS
try {
  await this.repo.insert({ userId, workspaceId });
} catch (e) {
  if (isUniqueViolation(e)) {
    throw new ConflictException("Already a member of this workspace");
  }
  throw e;
}

3. Page version — UNIQUE + retry (fix the race)

Instead of max()+1 alone 
# FastAPI — UNIQUE(page_id, version) + retry
async def create_page_version(session, page_id: int, content: str):
    for _ in range(5):
        last = await session.scalar(
            select(func.max(PageVersion.version)).where(PageVersion.version != None)
            .where(PageVersion.page_id == page_id)
        )
        n = (last or 0) + 1
        session.add(PageVersion(page_id=page_id, content=content, version=n))
        try:
            await session.commit()
            return n
        except IntegrityError:
            await session.rollback()
            continue  # another writer took this version
    raise HTTPException(503, "Could not allocate version — retry")
// NestJS — same idea
for (let i = 0; i < 5; i++) {
  const last = await this.versions.max("version", { pageId });
  const n = (last ?? 0) + 1;
  try {
    return await this.versions.save({ pageId, content, version: n });
  } catch (e) {
    if (!isUniqueViolation(e)) throw e;
  }
}
throw new ServiceUnavailableException("Could not allocate version");

4. Pessimistic lock (short critical section)

FOR UPDATE · commit fast 
# FastAPI
async def transfer_owner(db: AsyncSession, workspace_id: int, new_owner: int):
    ws = await db.scalar(
        select(Workspace).where(Workspace.id == workspace_id).with_for_update()
    )
    ws.owner_id = new_owner
    await db.commit()  # release lock immediately
// NestJS — QueryBuilder lock
await this.ds.transaction(async (manager) => {
  const ws = await manager
    .createQueryBuilder(Workspace, "w")
    .setLock("pessimistic_write")
    .where("w.id = :id", { id: workspaceId })
    .getOneOrFail();
  ws.ownerId = newOwner;
  await manager.save(ws);
});
