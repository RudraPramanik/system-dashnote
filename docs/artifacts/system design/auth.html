AuthN & AuthZ

Who you are, what you’re allowed to do, and how tenancy stays airtight — sessions vs JWT, OAuth2/OIDC in practice, RBAC/scopes, service auth, and tenant isolation as a design constraint.

Full curriculum DashNote-mapped FastAPI · NestJS

00 Overview

Security bugs in auth are rarely “forgot bcrypt” — they’re confused deputy, missing tenant filters, and tokens that outlive intent. Design AuthN and AuthZ as one system with explicit boundaries.

What this book covers
  1. AuthN vs AuthZ; passwords and secret hygiene
  2. Sessions vs JWT (and hybrids with Redis)
  3. OAuth2 / OIDC at a practical level
  4. RBAC, scopes, ABAC; service-to-service auth
  5. Tenant isolation end-to-end
Credentials→ AuthN→ Identity + tenant→ AuthZ→ Resource access
DashNote shape
Email/password → JWT access + refresh (HS256) → RequestContext(user, workspace, role) → RBAC helpers + SQL/Qdrant tenant filters. Docs: docs/documentation/auth.md.

01 AuthN vs AuthZ

Authentication (AuthN)

Who are you? Prove identity: password, OTP, WebAuthn, IdP token, mTLS cert.

Failures → 401 Unauthorized.

Authorization (AuthZ)

What may you do? Roles, scopes, policies, ownership, tenant membership.

Failures → 403 Forbidden (or 404 to hide existence).

Never conflate
A valid JWT means AuthN succeeded. It does not mean the user can delete someone else’s note. Check AuthZ on every sensitive operation — in the handler/service, not only in the UI.

02 Sessions vs JWT

Both can be secure. Pick based on clients, revoke needs, and ops cost.

Server sessionsJWT (bearer)
Client holds Opaque session id (cookie) Signed claims (often localStorage or cookie)
Server state Required (Redis/DB) Optional (stateless) or hybrid (denylist/allowlist)
Revoke Delete session — instant Hard until expiry unless blacklist / short TTL + refresh
Scale Shared session store Easy horizontal scale if fully stateless
CSRF Cookie sessions need CSRF defenses Bearer-in-header avoids classic CSRF; cookie JWT does not
Best for Browser-first apps, easy logout-all APIs, mobile, SPAs, service callers

Hybrid (common in production APIs)

  • Short-lived access JWT (5–15 min) — authorize API calls
  • Long-lived refresh — stored server-side (Redis allowlist), rotated on use
  • Logout — revoke refresh + blacklist access jti until exp
Guideline
If you need instant global logout and don’t want a denylist, prefer opaque sessions. If you need mobile + many services verifying tokens, prefer JWT + short TTL (+ refresh store).
DashNote · Covered (JWT hybrid)
Access ~15m + refresh ~30d; claims sub, wid, role, jti, typ. Redis: refresh allowlist + access blacklist. No cookie session middleware. Separate secrets: JWT_SECRET / JWT_REFRESH_SECRET, HS256.

03 Passwords & secret hygiene

  • Hash with bcrypt / argon2 / scrypt — never plain, never reversible encrypt for passwords
  • Constant-time compare; enforce max input length (bcrypt 72-byte limit)
  • Rate-limit login; lockout or backoff on brute force
  • JWT signing secrets: long, random, rotated; different for access vs refresh
  • Never log tokens or passwords; redact Authorization headers
DashNote · Covered
passlib bcrypt (+ legacy verify); login 5/min; global API rate limit. Register/refresh/logout only hit global limit — should tighten register too.

04 OAuth2 & OIDC — practical level

OAuth2 is delegation (access to APIs). OIDC adds identity (who logged in). You usually want OIDC for “Login with Google,” not raw OAuth2 alone.

Roles

  • Resource owner — the user
  • Client — your SPA / mobile / backend
  • Authorization server — Auth0, Okta, Keycloak, Google, Cognito
  • Resource server — your API

Flows you’ll actually use

FlowWhenNotes
Authorization code + PKCE SPA / mobile / native Default modern choice; no client secret on device
Authorization code Server-side web app Client secret stays on server
Client credentials Service-to-service No user; machine identity
Device code CLI / TV User approves on another device
Resource owner password Legacy only Avoid for new apps — trains users to type passwords into clients

OIDC essentials

  • id_token (JWT) proves identity; access_token calls APIs
  • Validate issuer, audience, signature, expiry — always
  • Scopes like openid profile email; API scopes separate from IdP profile scopes
  • Map IdP subject → local user row on first login
FastAPI gotcha
OAuth2PasswordBearer only extracts a Bearer token for OpenAPI/docs. It is not a full OAuth2/OIDC implementation.
DashNote · Gap (OIDC) / Partial (Bearer plumbing)
Uses OAuth2PasswordBearer for Authorization header extraction. Login is JSON email/password — not the OAuth password grant. Should be: OIDC (Auth0/Keycloak/Google) when you need SSO / social login; keep local JWT or exchange IdP tokens for your own access tokens.

05 RBAC & scopes

RBAC (role-based)

Assign roles; roles grant permissions. Simple to reason about for products with clear tiers.

  • Roles: owner, admin, member, viewer…
  • Enforce on routes (require_roles) and on domain objects (ownership, privacy)
  • Prefer deny-by-default

Scopes (capability tokens)

OAuth-style scopes (notes:read, files:write) limit what a token may do — useful for third-party apps and least privilege. Orthogonal to roles: a user may be admin but an integration token only has notes:read.

Permission matrix mindset

Actionowner/adminmember
View public noteYesYes
View private noteYesOwn only
Edit noteAny in workspaceOwn only
Invite membersYesNo
DashNote · Covered (RBAC) / Gap (scopes)
Workspace roles on JWT + require_roles; note/file helpers (can_view_note, can_manage_note); Qdrant build_rbac_filter. No OAuth scopes on tokens — role string only.

06 Beyond RBAC

ABAC / policies

Attributes: time, IP, resource tags, clearance. Engines: OPA, Cedar, Casbin.

ReBAC

Relationship-based (Google Zanzibar style): “user U is editor of doc D.”

Start with RBAC + ownership. Graduate when matrix sprawl or sharing graphs explode.

07 Tenant isolation — first-class constraint

In multi-tenant SaaS, the #1 AuthZ bug is IDOR across tenants: valid user, wrong workspace’s row.

Design rules

  1. Never trust client-supplied tenant id for authorization — take it from the token/session
  2. Every query: WHERE workspace_id = ctx.workspace_id (or equivalent)
  3. Cache keys, search filters, object storage prefixes — all tenant-scoped
  4. 401/403/404 policy: prefer 404 for cross-tenant reads to avoid enumeration
  5. Defense in depth: app filter + FK + optional Postgres RLS
JWT wid→ RequestContext→ SQL tenant_filter→ Qdrant / cache keys
Test it
Automated tests: user A in workspace 1 must never read/write workspace 2 resources by guessing IDs. This is non-negotiable CI coverage.
DashNote · Covered
wid → RequestContext → tenant_filter / TenantRepository / workspace-scoped cache keys / RBAC vector filters. Cross-tenant threads return 404. Should: FK workspace_id everywhere + consider RLS.

08 Service-to-service auth

Machines need identity too — workers, internal admin tools, partner integrations.

MechanismHowProsCons
API keys Header X-Api-Key / Bearer static Simple Rotation, leak blast radius; hash at rest
Client credentials (OAuth) Client id+secret → access token Short-lived; scopes Needs auth server
mTLS Both sides present certs Strong identity at transport Cert ops / mesh complexity
Signed service JWT Internal issuer, audience per service Fits microservice meshes Key distribution
Network only Private VPC, no auth Easy Fails when network boundary leaks — not enough alone
mTLS concept
TLS normally authenticates the server. Mutual TLS also authenticates the client with a certificate. Service mesh (Istio/Linkerd) often automates this. You still want app-level authorization (which service may call which route).
DashNote · Gap
No caller API keys / mTLS / service accounts for internal HTTP. “API keys” in config are provider credentials (Qdrant, LLM vendors) — outbound, not inbound AuthN. Workers trust the private Docker network today. Should be: when exposing internal admin or multi-service calls, add keyed or mTLS identity.

09 Token lifecycle

  • Issue — minimal claims; include tenant + role if needed for AuthZ
  • Validate — signature, exp, typ, issuer/audience when applicable
  • Rotate refresh — one-time use; detect reuse as theft signal
  • Revoke — logout, password change, admin disable
  • Storage on client — prefer httpOnly secure cookies for browsers; memory for SPA access tokens; never localStorage if XSS is a concern you can’t contain
DashNote · Covered
Refresh rotation + Redis presence check; logout blacklists access jti. Fail-open no-op token store when Redis off — OK for local; require Redis in prod.

11 Auth in the API contract

  • Document security scheme (Bearer, cookie, API key)
  • Consistent 401 vs 403 vs 404
  • Login endpoints: stricter rate limits + generic error messages (“invalid credentials”)
  • CORS: explicit origins; credentials only if cookies
DashNote
OpenAPI security when DEBUG; CORS from settings; ProxyHeaders for real IP on limits.

13 Code examples TOGGLE

1. Access token → request context

AuthN dependency 
# FastAPI — mirrors core/security/dependency.py
from dataclasses import dataclass
from fastapi import Depends, HTTPException
from fastapi.security import OAuth2PasswordBearer
from jose import jwt, JWTError

oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/auth/login")

@dataclass(frozen=True)
class RequestContext:
    user_id: int
    workspace_id: int
    role: str

async def get_current_context(token: str = Depends(oauth2_scheme)) -> RequestContext:
    try:
        payload = jwt.decode(token, JWT_SECRET, algorithms=["HS256"])
        if payload.get("typ") != "access":
            raise HTTPException(401, detail="Invalid access token type")
        if await token_store.is_blacklisted(payload["jti"]):
            raise HTTPException(401, detail="Token has been revoked")
        return RequestContext(
            user_id=int(payload["sub"]),
            workspace_id=int(payload["wid"]),
            role=payload["role"],
        )
    except (JWTError, KeyError, ValueError):
        raise HTTPException(401, detail="Invalid or expired token")
// NestJS — JwtAuthGuard + custom decorator
import { Injectable, CanActivate, ExecutionContext, UnauthorizedException } from '@nestjs/common';
import { JwtService } from '@nestjs/jwt';

@Injectable()
export class JwtAuthGuard implements CanActivate {
  constructor(private jwt: JwtService, private tokens: TokenStore) {}

  async canActivate(ctx: ExecutionContext) {
    const req = ctx.switchToHttp().getRequest();
    const raw = req.headers.authorization?.replace(/^Bearer\s+/i, '');
    if (!raw) throw new UnauthorizedException();
    try {
      const payload = await this.jwt.verifyAsync(raw, { secret: process.env.JWT_SECRET });
      if (payload.typ !== 'access') throw new UnauthorizedException();
      if (await this.tokens.isBlacklisted(payload.jti)) throw new UnauthorizedException();
      req.user = {
        userId: +payload.sub,
        workspaceId: +payload.wid,
        role: payload.role,
      };
      return true;
    } catch {
      throw new UnauthorizedException('Invalid or expired token');
    }
  }
}

2. RBAC: roles + resource rules

AuthZ 
# FastAPI — require_roles + note ownership (DashNote style)
def require_roles(*allowed: str):
    async def checker(ctx: RequestContext = Depends(get_current_context)):
        if ctx.role not in allowed:
            raise HTTPException(403, detail="Insufficient permissions")
        return ctx
    return checker

def can_manage_note(ctx: RequestContext, note) -> bool:
    if ctx.role in {"owner", "admin"}:
        return True
    return note.created_by == ctx.user_id

@router.delete("/{note_id}", status_code=204)
async def delete_note(
    note_id: int,
    ctx: RequestContext = Depends(get_current_context),
    db: AsyncSession = Depends(get_session),
):
    note = await repo.get_in_workspace(note_id, ctx.workspace_id)  # tenant filter!
    if not note:
        raise HTTPException(404, detail="Note not found")
    if not can_manage_note(ctx, note):
        raise HTTPException(403, detail="Insufficient permissions")
    await repo.delete(note)
// NestJS — RolesGuard + resource check in service
@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}
  canActivate(ctx: ExecutionContext) {
    const roles = this.reflector.get<string[]>('roles', ctx.getHandler());
    if (!roles?.length) return true;
    const { user } = ctx.switchToHttp().getRequest();
    return roles.includes(user.role);
  }
}

// service
async deleteNote(user: AuthUser, noteId: number) {
  const note = await this.notes.findInWorkspace(noteId, user.workspaceId);
  if (!note) throw new NotFoundException();
  const can =
    ['owner', 'admin'].includes(user.role) || note.createdBy === user.userId;
  if (!can) throw new ForbiddenException();
  await this.notes.remove(note);
}

4. Service API key (should-be pattern)

Machine callers 
# FastAPI — hash API keys at rest; compare with hmac.compare_digest
from fastapi import Header, HTTPException
import hashlib, hmac

async def require_service_key(x_api_key: str = Header(...)):
    digest = hashlib.sha256(x_api_key.encode()).hexdigest()
    row = await keys_repo.find_active(digest)
    if not row:
        raise HTTPException(401, detail="Invalid API key")
    return row  # includes service name + scopes
// NestJS — ApiKeyGuard
@Injectable()
export class ApiKeyGuard implements CanActivate {
  async canActivate(ctx: ExecutionContext) {
    const key = ctx.switchToHttp().getRequest().headers['x-api-key'];
    if (!key || !(await this.keys.verify(String(key)))) {
      throw new UnauthorizedException('Invalid API key');
    }
    return true;
  }
}
