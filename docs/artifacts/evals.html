Evals & Observability for AI systems

A practical field guide for measuring quality and seeing inside LLM apps — grounded in how DashNoteSystem ships RAG, agents, Langfuse, and Prometheus, and written so you can reuse the same playbook on any AI project.

Fundamentals Offline + online evals Tracing & metrics DashNote-ready

01 Why this matters

Traditional software fails loudly (exceptions, 500s). AI systems fail quietly — wrong citations, shallow retrieval, confident nonsense, tool loops that “succeed” with bad side effects.

Without evals

  • Prompt changes are vibes-driven
  • Model swaps break quality unnoticed
  • You discover regressions from users

Without observability

  • You cannot explain a bad answer
  • Latency/cost spikes are opaque
  • Tenant leaks stay invisible
Product principle
In DashNote, the product owns orchestration, retrieval, tenancy, and evals — not inference infrastructure. Hosted models are commodities; quality gates are the moat.

02 Evals vs observability

They answer different questions. You need both.

EvalsObservability
Question Is the system good enough? What happened on this request?
When CI, release gates, scheduled jobs Every (or sampled) production request
Output Scores, pass/fail, regressions Traces, logs, dashboards, alerts
DashNote today Manual gates (/ai/test-search, golden cases in docs) Langfuse RAG traces + Prometheus/Grafana
Change prompt / model / chunking → Offline eval gate → Deploy → Traces + metrics → Online signals → new goldens
Feedback loop
Production traces feed new eval cases. Eval failures drive instrumentation improvements. Treat them as one system, not two tool purchases.

03 The three layers of an AI app

Eval and observe at the layer that can actually fail — don’t only score the final answer.

Retrieval (RAG grounding)

Did we find the right chunks under the right tenant/RBAC constraints?

  • DashNote: WorkspaceVectorSearch + build_rbac_filter
  • Gate: cosine threshold (~0.4), workspace isolation, member private-note isolation
  • Route: GET /ai/test-search returns raw scores for tuning
# Mental model
query → embed → filter(workspace + RBAC) → ANN → score_threshold → chunks

Generation (answer quality)

Given context, is the answer faithful, useful, and cited correctly?

  • DashNote: RagService.answer → structured RAGAnswer
  • Critical: citations grounded against retrieved set — never trust LLM-hallucinated chunk IDs
  • Trace spans: retrieval → context_building → llm_generation

Agent / tool loop

Did the agent pick the right tools, stop correctly, and avoid unsafe side effects?

  • DashNote: LangGraph agent with search / note mutate / summarize tools
  • Governance: AutomationDecisionEngine for destructive actions (fail-safe block)
  • Eval focus: trajectory correctness, tool success rate, policy violations

04 Eval types (what to run when)

Most used taxonomy in AI engineering — memorize this table.

Score one stage in isolation (retrieval only, citation grounding only, classifier only).

Use when: debugging “is the bug retrieve or generate?”

Example: given query + corpus, assert top-k contains expected note_id / chunk_id.

Full path: query → retrieve → generate → structured output / tools.

Use when: release gates, model/prompt swaps, regression suites.

Tradeoff: slower and noisier; pair with component evals for diagnosis.

Offline: fixed dataset, repeatable, CI-friendly. Primary quality gate.

Online: live traffic — thumbs, edits, re-asks, latency, cost, safety flags. Catches distribution shift.

  • Regression: same suite before/after a change — must not drop below baseline.
  • Canary: small % traffic on new prompt/model with online metrics.
  • A/B: compare variants with statistical care (sample size, metric choice).

Non-negotiable for multi-tenant RAG.

DashNote golden: member B must not retrieve member A’s private notes; workspace_id always from JWT.

Fail these → block release even if answer quality looks high.

05 Datasets & golden sets

Your eval suite is only as good as the cases you freeze. Start small; grow from production failures.

Minimal golden schema (any project)

{
  "id": "rag-private-isolation-01",
  "surface": "rag",                 // rag | agent | retrieval | automation
  "input": {
    "message": "What is in Alice's private roadmap?",
    "role": "member",
    "user_id": "bob",
    "workspace_id": "ws_demo"
  },
  "expected": {
    "must_not_retrieve_note_ids": ["note_alice_private"],
    "answer_should_refuse_or_empty_grounding": true
  },
  "tags": ["security", "rbac", "p0"]
}

How to grow the set

  1. Happy path — questions your product must nail (10–30 cases).
  2. Hard negatives — similar-but-wrong docs, ambiguous queries.
  3. Security — cross-tenant, private notes, role boundaries.
  4. Adversarial — prompt injection via notes/files, tool abuse.
  5. Production mining — thumbs-down traces → add as golden with labels.
Anti-pattern
Don’t rewrite goldens every time the model fails. Fix the system or mark the case as expected hard. Constantly moving targets destroy regression value.

DashNote starter cases (recommended)

Practical scoring stack

Best first choice — cheap, stable, CI-safe.

  • JSON schema / Pydantic validation
  • Exact ID membership (citations ⊆ retrieved)
  • Regex / keyword must-include / must-exclude
  • RBAC filter assertions (empty forbidden set)

Compare to a labeled expected answer or expected chunk set.

  • Exact match / soft match on short answers
  • Embedding similarity to reference (use carefully)
  • Set overlap metrics on retrieved IDs

Use when answers are open-ended. Always calibrate against humans on a sample.

  • Score faithfulness, helpfulness, tone on 1–5
  • Require rationale + evidence spans from context
  • Use a different model family than the system under test when possible

07 Human & LLM judges

Judges are evaluators of quality — not a replacement for ground-truth security tests.

Human review

  • Gold standard for rubric design
  • Calibrate LLM judges (agreement %)
  • Spot-check production samples weekly

LLM-as-judge

  • Scales offline suites
  • Needs fixed rubric + few-shot examples
  • Can inherit bias / verbosity preference

Judge rubric template

You are evaluating a RAG answer.
Context chunks (only source of truth):
{{context}}

User question: {{question}}
Assistant answer: {{answer}}

Score each 1–5 with short evidence:
1) faithfulness — claims supported by context?
2) relevance — answers the question?
3) citation_quality — cited chunks actually support claims?

Return JSON: {faithfulness, relevance, citation_quality, rationale}
DashNote tip
Prefer deterministic citation checks first (already in product design). Use LLM judges for open-ended “was this helpful?” — not for tenancy.

08 Online & production evals

Offline suites prevent known regressions. Online signals catch the unknown.

SignalWhat it suggestsAction
Thumbs down / regenerate Quality miss Label → golden; inspect Langfuse trace
Re-ask same intent Answer incomplete Context budget / retrieval depth
Empty retrieval rate ↑ Index / embedding / threshold drift Check chunks_retrieved span
p95 latency ↑ Provider / retrieval slow Grafana + span latency_ms
Cost / tokens ↑ Prompt bloat or loops Agent tool-loop caps; budget
5xx on /ai/* Provider / infra failure Retry policy; degrade gracefully
Privacy
Never log raw JWTs. Prefer hashed or truncated IDs. Redact secrets from traces. DashNote metadata uses workspace_id, user_id, role — not tokens.

09 Observability pillars

Classic three pillars — applied to LLM systems.

Structured logs

Append-only events for ops and forensics. Prefer JSON.

DashNote schema: timestamp, level, logger, message + optional request_id, workspace_id, user_id, route, latency_ms.

{"timestamp":"...","level":"INFO","logger":"observability.langfuse_client",
 "message":"Langfuse client initialized","extra":{"host":"https://cloud.langfuse.com"}}

Distributed / LLM traces

One request → tree of spans with timing, I/O, tokens, cost.

For RAG, spans should mirror pipeline stages so you can see where time and failures live.

Metrics

Aggregates over time: rates, histograms, gauges. Drive SLOs and alerts.

DashNote HTTP: dashnote_api_http_requests_total, dashnote_api_http_request_duration_seconds → Grafana.

Later: custom metrics for rag_empty_retrieval_total, llm_tokens_total, agent_tool_errors_total.

Separation of concerns
HTTP metrics answer “is the API healthy?” Langfuse answers “why was this answer wrong?” Don’t force one tool to do both jobs poorly.

12 How to add evals (any AI project)

A repeatable recipe — use this on DashNote or a greenfield agent.

  1. Inventory surfaces

    List user-facing AI paths: chat, agent, classifiers, extractors. One surface = one suite folder.

  2. Write 15–40 goldens

    Include p0 security + happy path. Store as JSON/YAML under evals/datasets/.

  3. Implement runners

    Component runners first (retrieval IDs). Then E2E runners that call the same services production uses — not a duplicated “eval-only” pipeline.

  4. Score & baseline

    Emit a report JSON: pass rate, metric averages, failing case IDs. Commit a baseline file.

  5. Gate CI

    Fail PR if p0 cases fail or aggregate score drops > threshold (e.g. 3%).

  6. Wire production mining

    Weekly: export thumbs-down traces → label → promote to goldens.

Suggested DashNote layout

evals/
  datasets/
    retrieval_rbac.jsonl
    rag_grounding.jsonl
    agent_tools.jsonl
  runners/
    run_retrieval.py
    run_rag_e2e.py
  reports/                 # gitignored or artifact-only
  baselines/
    retrieval_rbac.json

Pseudo-runner (retrieval)

async def eval_case(case, search: WorkspaceVectorSearch):
    hits = await search.search(
        workspace_id=case["workspace_id"],
        user_id=case["user_id"],
        role=case["role"],
        query=case["query"],
        limit=8,
    )
    ids = {h.note_id for h in hits}
    assert case["expected_note_id"] in ids
    assert not (ids & set(case.get("forbidden_note_ids", [])))
    assert hits and hits[0].score >= case.get("min_score", 0.4)

13 How to add observability (any AI project)

Order of operations that avoids coupling and broken startups.

  1. Structured logging first

    JSON logs with request/tenant context. Idempotent setup at process start.

  2. Lazy vendor client

    Langfuse / OTEL exporter behind a getter that returns None when disabled. Never crash boot.

  3. Tracing facade

    trace / span context managers with no-op twins. Domain code imports the facade only.

  4. Instrument critical paths

    Start with the highest-value path (RAG answer). Add agent/tool spans next. Record latency + domain outputs.

  5. HTTP metrics

    Framework instrumentator → /metrics → Prometheus → 4–6 Grafana panels (rate, errors, p95/p99).

  6. Alerts & runbooks

    Alert on error rate and latency. Document “target DOWN” and “no traces” troubleshooting.

Pattern that scales
ai/ stays free of vendor SDKs · observability/ owns vendors · workers and HTTP share the same tracing helpers.

15 Ship checklist

Toggle items as you implement — progress is saved in this browser.

Evals

  • Inventory AI surfaces (chat, agent, automation, retrieval)
  • Create golden set with ≥5 p0 security / RBAC cases
  • Component retrieval runner (Hit@k + forbidden IDs)
  • Citation grounding assertion (IDs ⊆ retrieved)
  • E2E RAG runner on frozen dataset
  • Baseline file + CI fail on regression
  • Process for mining thumbs-down into goldens

Observability

  • JSON structured logging at process start
  • Lazy LLM-trace client (no-op when disabled)
  • Tracing facade; no vendor SDK in domain AI modules
  • RAG spans: retrieval → context → generation
  • Prometheus HTTP metrics + Grafana overview
  • Agent / tool spans (if you have an agent)
  • Runbook: missing traces, target DOWN, cost spike

Interview one-liners

Split retrieval vs generation. Retrieval: Hit@k / recall under RBAC filters. Generation: faithfulness + citation grounding on fixed context. Gate releases with offline goldens; use production traces for new cases.
Structured logs for ops; LLM traces for per-request trees (tokens, cost, spans); Prometheus for SLIs. Keep vendor SDKs behind a facade so domain code stays portable.
Tenancy is a correctness property. Eval private-note isolation and workspace filters as p0 — not as optional quality polish.
