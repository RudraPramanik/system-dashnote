Memory systems — short · long · prefs · forget

Thread history is not product memory. This guide separates working memory in the context window from durable preferences and facts — and maps what DashNote already ships.

Short-term Long-term Prefs Forget Gap guide

00 Memory ≠ context window alone

context.html is about compaction — fitting history + retrieval into a finite budget this turn. Memory is about what survives across turns and sessions and how you deliberately write, read, update, and forget it.

Context engineering

  • What enters this model call
  • Trim / summarize / order under budget
  • ContextBuilder: ≤70% history, ≥30% chunks
  • Rot when the window fills with noise

Memory systems

  • What persists beyond one window
  • Stores: messages, prefs, facts, digests
  • Policies: write · update · forget · conflict
  • Tenancy: never leak across users / workspaces
Rule of thumb
Compaction decides how to shrink what you already loaded. Memory decides what is worth storing so the next session does not start blank — without stuffing every past turn into the prompt.
User says → Write to store? → Read / select → Inject into context → Answer → Update / forget
LayerLives whereDashNote today
Working / short-term Thread messages + agent scratch + tool results AIThread / AIMessage + trim
Long-term prefs / facts Dedicated rows (user × workspace) Not yet
External knowledge Notes / Qdrant (RAG) Shipped — document memory, not user prefs

01 Short-term / working memory AIThread shipped

Everything the model needs for this conversation — recent turns, tool outputs, and ephemeral agent scratch — that can be trimmed or discarded when the budget bites.

Thread messages

User / assistant / tool rows in ai_messages. Loaded oldest→newest, capped by AI_THREAD_MESSAGE_LIMIT then ContextBuilder 70% budget.

Agent scratch

Plan notes, intermediate hypotheses inside LangGraph state. Ephemeral to the run unless you persist them.

Tool results

search_notes dumps re-enter the message list each iteration — high rot risk without truncation (see context.html).

Gap
DashNote ships truncate-oldest, not summarize. Early constraints can vanish when threads get long — that is a short-term memory failure mode, not “the model forgot.”

02 Long-term memory prefs / semantic missing

Facts and preferences that should survive new threads and new sessions — without requiring the user to restate them every time.

User preferences

“Prefer bullet answers”, “cite deadlines first”, output language. Soft rules, easy to update / forget.

Workspace facts

“Q3 launch is Sept 12”, “team uses Linear”. Durable but mutable; conflict resolution matters.

Episodic summaries

“Last week we decided to migrate auth.” Digests of past threads — hierarchical memory later.

Long-term kindWrite triggerRead triggerRisk
Preference Explicit (“always…”) or confirmed UI Every turn / matching intent Stale tone rules
Workspace fact Confirmed extract or note pin Query similarity / entity match Wrong / outdated fact
Episode digest Thread close / nightly job Related new thread Summary hallucination
Product framing
RAG notes are the team’s document memory. Long-term AI memory is the product’s relationship memory — preferences and distilled conversation state. Do not collapse them into one store without tenancy and conflict rules.

03 Episodic · semantic · procedural

Cognitive labels are useful when mapped to product storage — not as academic taxonomy for its own sake.

Episodic

What happened in a session. Thread turns, digests, “we tried X then Y.” Time-stamped; can expire.

Semantic

What is true (or believed). Workspace facts, entity attributes. Queryable like a knowledge base of small claims.

Procedural

How to behave. Prefs, playbooks, “always run search before answer.” Injected as soft system rules.

  • Episodic (partial) — raw AIMessage history; no hierarchical digests yet
  • Semantic (external) — note chunks in Qdrant; no dedicated AI memory fact table
  • Procedural (missing) — no preference store or memory tools

Semantic fact says launch is Sept 12; episodic digest from last week said Oct 1. Prefer newer confirmed write, or surface conflict to the user — never silently average.

04 Lifecycle — write · read · update · forget · conflict

Memory without a lifecycle becomes a junk drawer. Every store needs explicit policies for each verb.

Write → Read → Update → Forget → Conflict resolve
VerbPolicy questionsDashNote today
Write Explicit only? LLM extract? Confirm UI? Messages via persist_turn; no pref extract
Read Always inject? Top-k by similarity? Intent gate? Recent N messages + RAG chunks
Update Overwrite vs version? Who can edit? Append-only messages; no preference rows
Forget User delete, TTL, legal hold, soft delete? Thread deactivate; cascade messages
Conflict Newest wins? Higher confidence? Ask user? N/A (no multi-source memory store)
  • Safe default: only write prefs when the user says “always / never / remember that…”
  • Risky: silent LLM extraction of every claim → pollution and privacy issues
  • Hybrid: propose memory in UI → user confirms → row written
  • User: “forget my tone preference” → delete procedural row
  • TTL on episodic digests (e.g. 90 days)
  • Workspace leave / GDPR erase → cascade all memory for user_id
  • Compaction is not forget — dropped tokens still exist in ai_messages
# Pseudocode
if new.fact_key == old.fact_key and new.value != old.value:
    if new.confidence >= old.confidence and new.ts > old.ts:
        archive(old); write(new)
    else:
        flag_for_user(old, new)  # do not invent a merge
Don’t
Treat “not in this context window” as forgotten product data · auto-write unverified secrets · let conflict resolution invent a third value · skip forget paths for compliance.

05 Architecture patterns message store only

Four common product patterns — mix them; do not force everything into RAG.

1. Message store

Append-only conversation rows. Best for episodic short-term. DashNote: AIThread / AIMessage.

2. Preference store

Keyed rows (user × workspace × key). Fast inject into system / developer message. Not yet in DashNote.

3. Memory tool

Agent calls memory_save / memory_search. Explicit, auditable, slower. Fits agent slice.

4. RAG-as-memory

Embed “memory notes” and retrieve. Good for soft recall of long prose; weak for exact prefs and tenancy discipline.

When RAG notes vs dedicated memory rows

UseRAG / notesDedicated memory row
Team docs, specs, meeting notes Yes — primary No
“Always answer in bullets” Poor (noisy retrieval) Yes — preference key
Exact ID / deadline claim OK if in a note Yes if AI-owned fact + conflict policy
Last thread’s open questions No Episodic digest / thread summary
Cross-user personalization Dangerous if mis-scoped Only with user_id scope
Decision heuristic
If it must be exact, small, and always available → row. If it is long, fuzzy, and document-owned → RAG. If the agent should decide when to remember → memory tool (with confirm for sensitive writes). 
# Pattern mix for DashNote (target)
system + prefs (procedural rows)
+ fitted AIMessage history (episodic short)
+ optional digest (episodic long)
+ RAG chunks (document semantic)
+ optional memory_search hits (semantic AI store)

06 Privacy & tenancy workspace filter shipped

Memory multiplies blast radius. A leaked preference or fact across workspaces is a trust failure — not a “helpful” feature.

Already enforced

  • WorkspaceTenantMixin on AIThread
  • ThreadRepository: workspace_id on every query
  • Cross-workspace thread_id → error (400 chat / 404 thread)
  • RAG retrieval RBAC-scoped to workspace

Must keep when adding LTM

  • Composite scope: workspace_id + optional user_id
  • No “global” preference without explicit product decision
  • Memory tool args cannot override tenant from JWT
  • Forget / export / erase hooks for user data
Never
Inject memory retrieved without workspace filter · share user prefs across workspaces · store secrets (API keys, passwords) as “helpful memory” · return another user’s episodic digests via similarity search. 
# ThreadService — structural tenancy (already)
thread = await repo.get_thread(db, thread_id=..., workspace_id=...)

09 How to implement next in DashNote

Ordered steps that respect import laws and existing tenancy.

  1. Ship thread summarization first (P0)

    Closes the short-term gap before adding new stores. See context.html compaction sketch — keep last 4–6 turns raw + structured digest.

    # ai/memory/compaction.py (new)
async def compact_history(messages: list[dict]) -> list[dict]:
    if estimate(messages) < threshold:
        return messages
    old, recent = messages[:-6], messages[-6:]
    digest = await structured_summary(old)  # goals, decisions, open Qs
    return [{"role": "system", "content": format_digest(digest)}, *recent]
